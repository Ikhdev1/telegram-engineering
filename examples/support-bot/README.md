# Support bot — рабочий пример aiogram 3 + SQLite

Самодостаточный пример поддержки на Python `>=3.12`, `aiogram==3.31.0` и
стандартном SQLite. Это не scaffold: клиент создаёт заявку через три шага,
хранит её в SQLite, видит только свои обращения; оператор обрабатывает
назначенные ему заявки; администратор назначает операторов; владелец управляет
администраторами. Роли, настройки и аудит переживают перезапуск.

Все пользовательские экраны работают в личном чате. Тексты и кнопки — на
русском; Telegram-клиент и живой API в автотестах не используются.

## Что реализовано

- Четыре уровня доступа: клиент, оператор, администратор, владелец.
  Владелец задаётся только `OWNER_ID` из доверенного окружения; режима
  «первый нажавший /start становится владельцем» нет.
- Создание заявки: тема → описание → предпросмотр → одноразовое подтверждение.
  Черновик, подтверждающий token и все шаги лежат в SQLite, поэтому переживают
  рестарт; «Назад» доступен там, где есть предыдущий шаг, «Отмена» — на всех
  шагах создания.
- Клиент: «Мои заявки» с пагинацией, карточка, отмена открытой заявки.
  Чужая карточка отвечает обезличенным «не найдена или недоступна».
- Администратор: очередь `new/assigned`, карточка, назначение и переназначение
  оператора. Назначение проверяет актуальную роль оператора и версию заявки.
- Оператор: личная очередь только назначенных заявок, закрытие заявки как
  решённой. Роль и назначение перечитываются из БД при каждом действии.
- Владелец: выдача/снятие администраторов. Администратор: выдача/снятие
  операторов. Изменение роли — два шага: numeric ID, затем одноразовое
  подтверждение с TTL. Владельца нельзя назначить или снять через бота.
- Настройки: пользователь включает/выключает уведомления о статусе своих
  заявок; администратор/владелец включает/выключает приём новых заявок.
  Переключатель приёма использует CAS по версии настройки.
- Аудит: actor, действие, объект, результат, UTC-время. Пишется в той же
  транзакции, что и бизнес-изменение; текст заявок и секреты туда не попадают.
- Повторы: `(bot_id, update_id)` и мутация коммитятся одной транзакцией.
  Повторная доставка возвращает сохранённый outcome и не выполняет действие
  второй раз. Отдельный двойной клик с новым `update_id` защищён статусом,
  версией или одноразовым token.
- HTML: весь пользовательский текст экранируется. Размер экрана считается по
  видимому тексту после разбора сущностей, а не по длине HTML-источника,
  поэтому 2000 символов `<`, `&` или `>` в описании не блокируются. Для
  астральных символов используется локальный консервативный запас; если он
  всё же вызывает сокращение, экран показывает маркер «текст сокращён».
  Callback data строится только через один encoder и проверяется на лимит
  64 байта UTF-8.
- SQLite: явная миграция по `PRAGMA user_version`, отдельное соединение на
  каждую операцию, `BEGIN IMMEDIATE` для записи, WAL, `busy_timeout`.
- Polling: один процесс, собственный цикл `getUpdates`. Offset двигается
  только после успешной обработки обновления; ошибка handler'а не подтверждает
  update. Существующий webhook не удаляется и не переключается молча:
  приложение откажется стартовать.

## Требования

- Python 3.12+.
- Постоянный локальный диск для файла SQLite.
- Токен бота и numeric ID владельца — только в окружении процесса.

## Установка

Из директории `examples/support-bot`:

```text
python -m venv .venv
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

POSIX shell:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
```

`pyproject.toml` позволяет альтернативно выполнить `python -m pip install .`;
для запуска из этой директории editable install не обязателен.

## Конфигурация

Переменные читаются из окружения процесса. Файл `.env` **не загружается
автоматически**; `.env.example` — только шаблон с пустым токеном.

| Переменная | Обязательна | Значение |
|---|---|---|
| `BOT_TOKEN` | да | Токен BotFather. В публичный репозиторий и логи не попадает. |
| `OWNER_ID` | да | Положительный numeric Telegram ID владельца, не `@username`. |
| `SUPPORT_DB_PATH` | нет | Путь к SQLite-файлу, по умолчанию `./support_bot.sqlite3`. |

Windows PowerShell:

```powershell
$env:BOT_TOKEN = "PASTE_LOCAL_TOKEN_HERE"
$env:OWNER_ID = "123456789"
$env:SUPPORT_DB_PATH = "./support_bot.sqlite3"
python -m support_bot
```

POSIX shell:

```bash
export BOT_TOKEN="PASTE_LOCAL_TOKEN_HERE"
export OWNER_ID="123456789"
export SUPPORT_DB_PATH="./support_bot.sqlite3"
python -m support_bot
```

Токен вводится локально или в secret manager хостинга. Не отправляйте его в
чат, задачу или репозиторий. Если токен раскрыт, отзовите его у BotFather.

Проверка CLI и справки:

```text
python -m support_bot --help
```

## Запуск и проверки

Обычный запуск (long polling, один consumer):

```text
python -m support_bot
```

Офлайн-smoke без токена, сети и Telegram-аккаунта:

```text
python -m support_bot --offline-smoke
```

Smoke создаёт временную SQLite-базу, поднимает настоящий aiogram `Dispatcher`,
прогоняет обновления через `Dispatcher.feed_raw_update` и использует
no-network fake session только для исходящих методов. Он проверяет создание
заявки, экранирование, видимость своих/чужих данных, выдачу и снятие ролей,
назначение, закрытие оператором, повтор `update_id`, новый клик по старой
кнопке, рестарт и одну конкурентную гонку назначения. Результат — JSON с полем
`ok`, числом проверок и их списком. При сбое JSON содержит `ok: false`,
`error` и уже пройденные проверки; код выхода — 1. Успех — код 0. Smoke
закрывает fake-транспорты и не оставляет открытых соединений SQLite.

Поведенческие тесты (stdlib `unittest`, без pytest и без сети):

```text
python -m unittest discover -s tests -v
```

## Роли и первые действия

1. Указать `OWNER_ID` в окружении и запустить бота.
2. Владелец открывает личный чат: `/start` → «Управление» → «Роли» →
   «Выдать админа» → отправляет numeric ID → подтверждает.
3. Администратор: «Управление» → «Роли» → «Выдать оператора» → numeric ID →
   подтверждение.
4. Клиент: «Создать заявку» → тема → описание → предпросмотр → «Подтвердить».
5. Администратор: «Управление» → «Очередь заявок» → карточка →
   «Назначить оператора».
6. Оператор: «Моя очередь» → карточка → «Закрыть как решённую».

Целевой пользователь должен хотя бы раз открыть бота (`/start`), иначе выдать
ему роль нельзя. Username — только подсказка; источник истины — numeric ID.
Все административные действия доступны только в личном чате. Отзыв роли
немедленно влияет на уже отправленные кнопки: сервер перечитывает биндинги и
объект при каждом callback. Если у оператора отозвали роль после назначения,
заявка остаётся назначенной, но оператор не может её закрыть; администратор
может переназначить её другому оператору.

Настройки:

- «Настройки» у пользователя — уведомления о назначении и решении его заявок.
- «Управление» → «Настройки» — приём новых заявок. Выключение блокирует
  создание и подтверждение новых заявок, но не удаляет существующие.

## Данные, миграции и восстановление

Схема версии 1 создаётся при старте. Версия хранится в `PRAGMA user_version`;
миграции применяются по порядку в `BEGIN IMMEDIATE`. Повторный запуск на
актуальной базе ничего не меняет; база с более новой версией отвергается.
Обратных миграций нет. Если файл уже занят другим процессом или активным
писателем, startup завершается понятным `ConfigError` о single-process
ограничении; автоматических retry нет.

Таблицы: `users`, `role_bindings`, `drafts`, `requests`, `user_settings`,
`settings`, `audit_events`, `processed_updates`, `role_pending`.

Перед обновлением кода:

1. Остановить процесс.
2. Сделать backup файла БД вместе с `-wal`/`-shm` либо использовать
   `sqlite3 support_bot.sqlite3 ".backup backup.sqlite3"`.
3. Запустить новую версию; миграция пройдёт до начала polling.

SQLite рассчитан на **один процесс** и один polling consumer. Не запускайте
несколько реплик с одной базой и не используйте один токен в двух процессах.
Для нескольких процессов, повышенной конкуренции или внешнего API нужна
PostgreSQL (или другая БД с блокировками) и отдельный план миграций; этот
пример такую поддержку не изображает.

### Почему offset не теряет действие

Стандартный `Dispatcher.start_polling()` в aiogram переживает исключение
handler'а внутри `_process_update` и продолжает цикл; полагаться только на
`handle_as_tasks=False` для гарантии сохранности нельзя. Поэтому пример
использует собственный цикл `getUpdates`:

1. Пришла пачка updates — offset ещё не подтверждён.
2. Update обрабатывается через `Dispatcher.feed_update`, который пробрасывает
   исключение наружу.
3. При ошибке update повторяется (до 3 попыток, с задержкой). Если попытки
   исчерпаны, процесс останавливается с `PollingError`, **не** вызывая
   `getUpdates` с новым offset. Telegram оставит update для повторной доставки.
4. DB-мутация и claim `(bot_id, update_id)` коммитятся одной транзакцией.
   Если исключение случилось после commit, повтор видит готовый outcome и не
   повторяет side effect; если до commit — повтор выполняет действие.
5. Offset увеличивается только после успешного возврата handler'а.

Это защищает committed DB action от потери, но не обещает exactly-once
отправку сообщений в Telegram: сетевая отправка не входит в SQLite-транзакцию.

На POSIX при SIGINT/SIGTERM цикл останавливается, текущий `getUpdates`
отменяется, Bot session и FSM-хранилище закрываются. Прерванный update
остаётся неподтверждённым; после рестарта Telegram доставит его снова, а dedup
предотвратит повтор бизнес-изменения. На Windows asyncio не поддерживает
`add_signal_handler`: gracefully обрабатывается только Ctrl+C/KeyboardInterrupt;
внешний SIGTERM/`taskkill` завершает процесс без этого пути. SQLite-транзакции
атомарны, а unconfirmed update будет доставлен после рестарта — данные не
теряются.

## Границы примера

- Только личные чаты. В группах бот просит открыть личный чат и не публикует
  карточки; административные callback из группы отклоняются.
- Только polling. Webhook не настраивается и не удаляется; при активном
  webhook запуск завершается ошибкой, чтобы оператор выбрал транспорт явно.
- Уведомления и экраны отправляются best-effort. Ошибка `SendMessage`/
  `EditMessageText` (403, 429, сеть) логируется с причиной и не останавливает
  polling и не заставляет повторять уже зафиксированную бизнес-операцию;
  `retry_after` из 429 попадает в лог, но экран автоматически не повторяется.
  Ошибки БД/бизнес-инвариантов до commit по-прежнему проходят через retry и,
  если исчерпаны, останавливают polling без подтверждения update.
- Telegram не даёт общего idempotency key для `sendMessage`; exactly-once
  доставка не обещается. Источник истины — БД и экран статуса.
- Нет вложений, файлов, тем форума, групп, рассылок, напоминаний и фоновых
  задач. Нет мультиарендности и i18n.
- `processed_updates` и `audit_events` не чистятся автоматически. Для долгой
  эксплуатации нужна отдельная retention-политика с учётом требований аудита
  и горизонта повторной доставки Telegram.
- Один owner из конфигурации. Смена владельца — только через доверенное
  развёртывание/окружение, не через чат.
- Живой Telegram API, webhook и визуальный рендер в клиенте автотестами не
  проверяются; офлайн-smoke проверяет dispatcher, доменные инварианты,
  SQLite и исходящие payload'ы через fake transport.

## Структура

```text
support_bot/
  __main__.py      # python -m support_bot
  cli.py           # --help, --offline-smoke, обычный polling
  config.py        # BOT_TOKEN / OWNER_ID / SUPPORT_DB_PATH
  db.py            # соединения, WAL, user_version, миграция
  service.py       # публичный фасад SupportService
  service_core.py  # dedup, транзакции, права, row-конвертеры
  request_service.py   # черновики, заявки, очередь, назначение
  governance_service.py # роли, настройки, аудит
  handlers.py      # aiogram router, экраны, best-effort уведомления
  ui.py            # HTML-экраны и inline-клавиатуры
  callbacks.py     # bounded callback encoder/parser
  offline.py       # no-network fake session + smoke сценарий
  app.py           # Bot/Dispatcher, offset-safe polling, shutdown
tests/
  test_*.py        # stdlib unittest
```
