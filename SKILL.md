# Telegram: продукт, интерфейс и бэкенд

Создавай законченный пользовательский сценарий, а не один обработчик `/start`. Сначала установи поверхность Telegram и бизнес-правила; затем согласуй удобные экраны и реализуй их вместе с хранением, серверными правами и проверкой. Отвечай на языке пользователя.

## 1. Установи объём и задай полезные вопросы

Отдели запрос «создать бота» от «оформить пост» и «работать от моего аккаунта». Bot API, Mini App и клиентский Telegram API — разные поверхности и доверительные границы.

Извлеки известное из запроса и файлов. Если brief полный — сразу действуй. Если существенных данных нет — задай одним блоком 3–7 коротких вопросов с вариантами и рекомендуемыми значениями; конкретные коллизии и права важнее выбора цвета кнопок. Не задавай анкету на 30 пунктов и не требуй токен в переписке. При просьбе «без вопросов» выбери безопасные допущения, явно назови их; не выдумывай согласованные бизнес-правила.

Результат этого шага: цель, аудитория, поверхности, основные действия, роли, данные, интеграции, часовой пояс/сроки и критерии готовности. Неизвестный секрет блокирует только реальное подключение, не локальную реализацию.

## 2. Покажи взаимодействие до реализации

Когда brief определён, дай краткую карту меню и 1–2 ключевых экрана: текст → кнопки по строкам → переход → кто имеет доступ. Отдельно покажи подтверждение опасного действия, пустой список и истёкшую кнопку. Зафиксируй правила Back/Cancel и восстановления после рестарта. Пока пользователь просит только уточняющие вопросы, используй компактную форму из discovery.md: подробные экраны принадлежат следующему этапу.

По умолчанию: inline-навигация рядом с объектом; команды для возврата и помощи; reply-клавиатура только когда действительно полезна. Админка в боте достаточна для небольших списков и операций. Mini App или отдельная веб-админка нужны только при сложных таблицах, массовых действиях и формах либо по требованию. Не навязывай сайт.

## 3. Проверь API, а не память модели

В Telegram есть **обычные** сообщения `sendMessage` и **rich messages** `sendRichMessage`. Таблицы, заголовки и details в rich HTML нельзя отправлять как обычный `parse_mode=HTML`. Rich Markdown — не MarkdownV2. Кнопки в rich-тексте также отличаются от `InlineKeyboardButton`.

Снимок источников проверен 2026-10-26: Bot API 10.3, aiogram 3.31.0. Это не вечная фиксация версии: проверь текущий контракт метода, установленный SDK и changelog перед использованием нового поля. При расхождении старого FAQ и контракта метода приоритет у актуального контракта и changelog. Офлайн пометь непроверенное; не придумывай поля.

Для поддерживаемых методов запускай локальный валидатор на **реальном сформированном payload**, а не на переписанном специально для теста примере: `python scripts/telegram_payload.py --method METHOD --file request.json --json` из каталога скилла. Исправь найденные ошибки; warnings означают конкретную границу локальной проверки, не повод скрыть сообщение. Валидатор не отправляет данные и не доказывает права, актуальность API или визуальный рендер. Для неподдерживаемого метода используй официальный контракт/SDK и честно обозначь отсутствие проверки.

## 4. Реализуй вертикальный сценарий

Собери один модульный сервис в текущем стеке. Для нового Python-проекта разумная база — поддерживаемый Python и aiogram 3 с закреплёнными зависимостями; для существующего TypeScript-проекта сохрани его SDK, например grammY. Бэкенд не обязан иметь публичный HTTP API. Добавляй PostgreSQL для конкурентных записей и нескольких процессов; SQLite годится для небольшого однопроцессного проекта с понятными ограничениями. Redis, очередь и отдельный worker добавляй по реальной потребности, не автоматически.

Отделяй Telegram handlers/renderers от бизнес-операций и доступа к данным. Храни бизнес-состояние в БД, а не только в FSM. Авторизуй каждую команду, callback и API-операцию на сервере: роль **и** доступ к конкретному объекту **и** актуальное состояние. Скрытое меню не защита.

Сначала проведи основной путь от сообщения до записи в БД и видимого результата, затем добавь заявленные настройки, админские сценарии и ошибки. Не выдавай заглушку, `pass`, фиктивную интеграцию или in-memory demo за готовый бэкенд.

Для нового небольшого Python-бота прочитай рабочий пример `examples/support-bot`: используй проверенные транзакционные и UI-паттерны, а не копируй весь продукт. Сначала запусти `python -m support_bot --offline-smoke` из его каталога; это реальный dispatcher и временная БД с явно локальным transport. Пример ограничен одним polling-процессом/SQLite. Для другого стека перенеси инварианты, не вводи Python-зависимость ради скилла. Доменные операции выбирай по recipes, а не превращай support bot в универсальный магазин через фиктивные кнопки.

## 5. Проверь и передай

Пройди [delivery.md](references/delivery.md): happy path, чужой объект/роль, повторный update, двойной клик, конкурентное действие, устаревшая кнопка, рестарт, форматирование с эмодзи и спецсимволами. Запусти реальный изменённый путь локально; при разрешённом тестовом боте проверь видимые экраны в Telegram. Без токена честно отдели локальную проверку от живой и визуальной.

Передай: работающие файлы, точные команды запуска/миграций/проверки, безопасный `.env.example`, описание меню и ролей, выполненные проверки и оставшиеся внешние предпосылки. Обнови состояние проекта и существующую документацию. Токены, session-файлы и персональные данные не включай в отчёт, логи или коммит.

Если пользователь просит «проверить сам скилл», следуй разделу проверок в [README](README.ru.md); в исходном пакете дополнительно есть `evals/README.md`: guidance-only ответ недостаточен, нужен исполняемый результат и независимая проверка. Симуляцию выбора description, HTML-макет, SDK-сериализацию и живой Telegram всегда называй разными уровнями доказательства.

## Ошибки, которые нужно предотвращать

- «Таблиц в Telegram нет» — проверь rich messages, а не ограничивайся старым parse mode.
- «32768 в sendMessage» — нет, у обычного текста собственный лимит.
- «Первый пользователь становится владельцем» — владельца задаёт доверенная конфигурация.
- «callback_data говорит, что это admin» — личность берётся из update, права — из серверного хранилища.
- «Пометил update обработанным до действия» — после сбоя действие потеряется; используй атомарное завершение или durable inbox.
- «Редактирую общее сообщение, чтобы показать личное меню» — это изменяет экран для всех; нужна личка или ephemeral API.
- «Все функции Telegram доступны боту» — право, поверхность и версия проверяются для каждого метода.
