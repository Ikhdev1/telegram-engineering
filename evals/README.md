# Проверка применения скилла

Сценарии проверяют результат работы ИИ, а не только наличие нужных слов в инструкции. Запускайте каждый в отдельном каталоге; не используйте реальный токен или рабочую БД.

## Наборы

- `evals.json`: rich formatting, устойчивые admin callbacks, компактное уточнение требований.
- `application.json`: создание исполняемого SQLite-сценария, исправление реального payload, запуск reference bot.
- `check_booking.py`: независимая проверка созданного `Store` через настоящую БД, рестарт и два конкурентных писателя.
- `triggers.json`: 10 целевых запросов и 10 близких отрицательных примеров для выбора скилла.

Для baseline сохраните копию предыдущего скилла и не давайте исполнителю читать новую версию или ответы другого варианта. Запускайте одинаковый prompt в свежем контексте с прежним и новым скиллом. Нельзя превращать старую ошибку в успех редактированием ответа: после изменения инструкции создаётся новая итерация.

## Исполняемый сценарий

Дайте ИИ задачу `booking-build` из `application.json` и отдельный выходной каталог. После получения `booking.py` выполните из корня пакета:

```bash
python evals/check_booking.py path/to/generated/booking.py
```

Это проверяет семантику: уникальную активную запись, доступ к собственным данным, повтор доставки, перезапуск, отмену/повторное использование слота и реальные конкурентные соединения. Генерируемый код не является частью библиотеки скилла и не должен автоматически исполняться без просмотра в доверенной среде.

## Проверка description

В свежем контексте покажите только description скилла и один запрос из `triggers.json`; потребуйте решение `use_skill` и короткое объяснение. Сравните его с `should_trigger`. Это **симулированный routing**, не доказательство, что конкретный host автоматически прочитает SKILL.md. Для прямой проверки host нужны его реальные журналы выбора/вызова скилла. Один ответ на запрос — smoke; для измерения устойчивости повторяйте выбор и фиксируйте расхождения, не подбирайте ответы вручную.

## Фиксация результатов

Для каждого результата сохраняйте prompt, использованную версию, output, выполненные команды, их результаты и ограничения. Градация: `expectations` с полями `text`, `passed`, `evidence`; отдельно `summary` с `passed`, `failed`, `total`, `pass_rate`. Указывайте доказательство для каждого pass, не проверяйте только имя файла или присутствие API-идентификатора.

Отчёт различает:
- статическую проверку payload;
- работу настоящего локального dispatcher и БД;
- визуальную проверку иллюстративной галереи;
- реальную отправку/вид Telegram-клиента, если отдельно разрешены.

Отсутствующие токены/стоимость/тайминги не вычисляйте из длины текста и не заполняйте вымышленными числами. Сырые разговоры, имена пользователей, абсолютные локальные пути и секреты не включайте в публичный архив.
