# Проверка, запуск и передача

## Локальная готовность

Сначала закрепи поддерживаемые версии в принятом lockfile/requirements; не пиши «latest» как воспроизводимый деплой. В конфиге проверь необходимые значения на старте. `.env.example` содержит только имена переменных и пустые/демонстрационные значения: BOT_TOKEN, OWNER_IDS, DATABASE_URL, WEBHOOK_SECRET при webhook. Не добавляй REDIS_URL/домен, если они не используются. Автомиграции/создание схемы не должны случайно стереть данные.

Прогони изменённый путь как программу: process start → конкретный update/action → permission/DB transition → renderer/result. Для имеющихся БД и бота используй отдельные временные данные/тестового бота; не подменяй продакшен polling/webhook. Permanent tests должны ловить поведение и инварианты, не копии текста/число кнопок/сам факт вызова mock.

## Минимальные сценарии при создании бота

| Сценарий | Наблюдаемый результат |
|---|---|
| Новый пользователь `/start` → основное действие | Полезное меню, правильная запись в БД и итоговый экран |
| Неверный ввод/пустой список | Понятный текущий шаг/переход без потери уже принятого ввода |
| Назад/отмена на промежуточных шагах | Нет незаявленной мутации; состояние предсказуемо |
| Чужой объект/другая роль/tenant | Отказ без утечки данных и побочного эффекта |
| Отзыв роли + старая admin-кнопка | Новый отказ, несмотря на видимость старой кнопки |
| Повтор update и отдельный двойной клик | Одна бизнес-операция; корректный повторный outcome |
| Два конкурентных претендента на слот/переход | Разрешён ровно один переход; второй видит конфликт/актуальное состояние |
| Рестарт/сбой между inbox и обработкой | Незавершённая работа восстанавливается; committed не повторяется |
| Ошибка внешнего сервиса/429/403 | Правильная категория/состояние, без бесконечного retry и fake success |
| Спецсимволы, emoji, длинный текст, rich/table/details | Правильная сериализация и видимое оформление в разрешённом клиенте |
| Потеря доступа в канале/тема группы | Нет публикации в неверный чат/топик и нет ложного «готово» |

Для короткой правки выбери только затронутые сценарии. Для гонок используй реальную выбранную БД и независимые транзакции, а не один sequential mock. Проверяй допустимые и запрещённые переходы/границы, не внутренние имена функций. Можно использовать временный smoke script, затем удалить его; доказательства сохраняются в отчёте.

## Polling или webhook

Они взаимоисключающие для одного токена. Локально обычно один polling-процесс; продакшен polling тоже допустим для одного сервиса, webhook не является обязательным признаком качества.

**Polling:** единственный потребитель; подтверждение offset только после обработки или надёжной записи inbox. Проверь поведение SDK, если он подтверждает updates раньше фоновых handlers. Запуск второго процесса на prod-токене может забрать updates или дать конфликт. `deleteWebhook(drop_pending_updates=true)` — потеря очереди, не стандартный startup-шаг.

В aiogram 3.31.0 `handle_as_tasks=False` означает ожидание handler, но **не гарантирует повтор после его исключения**: внутренний `_process_update` ловит/logs exception и считает update обработанным, после чего polling может сдвинуть offset. Если потеря бизнес-действия недопустима, сохрани update в durable inbox до dispatch и восстанавливай pending либо используй явный цикл getUpdates → `feed_update` → advance offset только после успешной устойчивой обработки. Проверь fault-сценарий: ошибка БД до commit не должна подтверждать/терять update. [Исходный dispatcher](https://github.com/aiogram/aiogram/blob/v3.31.0/aiogram/dispatcher/dispatcher.py) первичен для этого поведения.

**Webhook:** HTTPS, проверка отдельного `secret_token` из заголовка `X-Telegram-Bot-Api-Secret-Token`, лимит тела запроса, валидный JSON/update. Секрет сравнивается безопасно; токен бота не нужен в публичном route. Возвращай 2xx только когда результат обработан или update устойчиво сохранён для обработки. `create_task()` перед 200 без durable storage теряет update при падении. Неверная аутентификация отклоняется. В SDK background/webhook handlers проверь этот момент явно. В callback-запросах учти быстрый ACK: не клади короткоживущие действия в долгую очередь без обработки UX.

На cloud Bot API проверь поддерживаемые порты/сертификат по setWebhook; `allowed_updates` укажи по нужным типам, иначе часть событий (например, chat_member) может не приходить. Перед переключением транспорта проверяй `getWebhookInfo`, pending/error и текущую конфигурацию. Не переключай работающий бот без явного разрешения.

## Эксплуатация

- Запускай сервис с понятной restart policy выбранного supervisor/container, без запуска от root по необходимости по умолчанию; не ставь Kubernetes без причины.
- Постоянный том БД, миграции перед совместимым стартом, backup и проверенный restore. Для релиза с необратимой миграцией откат приложения не равен откату данных.
- Graceful shutdown: перестать принимать новую работу, корректно завершить/вернуть в pending выполняемую, закрыть сессии БД/SDK. Не останавливай существующие боты и watchdog без команды оператора.
- Логируй безопасный correlation, update_id и тип события/ошибки; токены в URL, полный initData, личную переписку и session string редактируй/не записывай. Нужный минимум health/readiness — без публичного вывода секретов и роли owner.
- Напоминания/рассылки должны переживать рестарт, иметь статус/дедуп по получателю и событию, scope/отписку. Учитывай 429/retry_after и лимиты чата/бота; paid broadcasts не включай без согласованного бюджета.

## Реальная проверка Telegram

С разрешённым отдельным тестовым ботом и чатами проверь минимум: `/start`, главное действие, «Назад», «Отмена», admin как разрешённый и обычный пользователь, stale callback, итог после рестарта, пример rich-сообщения. В Telegram-клиенте посмотри мобильную ширину, переносы кнопок, details, таблицу, URL и тему чата. Показ JSON в консоли не доказывает визуальное оформление. Не публикуй в реальные каналы ради smoke.

Без токена можно полностью проверить domain/DB/permissions, SDK-модели и сериализацию, локальный ingress и render payload. Укажи: **живой Telegram API и клиентский вид не проверены**. Не объявляй это готовым подключённым ботом. Токен оператор вводит локально/на хостинге, не в переписке.

## Передача результата

Сообщи компактно:
1. Где создано/изменено, какие пользовательские пути доступны.
2. Точные команды установки, конфигурации секретов локально, миграций, старта и проверки из README проекта.
3. Как задаётся owner, выдаются/отзываются роли, где админка и какие настройки меняются.
4. Выполненные проверки с наблюдаемым результатом; отдельно непроверенные внешние интеграции/клиенты.
5. Необходимые внешние предпосылки и безопасный rollback/restore по требованию проекта.

Не выдавай пустые разделы меню и конфигурационные заглушки за готовые функции. Не коммить, не выкладывай публично и не включай платные функции без соответствующей задачи.
