# Доменные рецепты: запись, поддержка, магазин, клуб, публикации

Пять рецептов для типовых Telegram-продуктов. Это **не пять готовых ботов** и не обязательный стек: каждый файл задаёт вопросы, экранный путь, данные, инварианты, границы транзакций, отказы и проверяемые сценарии. Реализацию встраивай в существующий проект; не переписывай его ради рецепта.

Снимок: **26.10.2026**, контекст **Bot API 10.3**. Точные методы, поля и ограничения сверяй с [официальным Bot API](https://core.telegram.org/bots/api.md) и установленной версией SDK.

## Рецепты

| Рецепт | Когда брать | Критический инвариант | Основной путь |
|---|---|---|---|
| [Запись на услуги](recipes/booking.md) | Слоты, исполнители/ресурсы, перенос и отмена | Нет пересечения активных интервалов сверх вместимости; DST не размывает время | Услуга → слот → данные → подтверждение → «Мои записи» |
| [Поддержка](recipes/support.md) | Обращения, очередь, операторы, внутренние заметки | Заметка `internal` никогда не попадает клиенту; у обращения один исполнитель | Новая заявка → очередь → карточка → ответ/заметка → закрытие |
| [Магазин](recipes/shop.md) | Цифровой товар в Stars или физический заказ | Товар/доступ выдаются только после проверенного `successful_payment` | Каталог → заказ → счёт → оплата → выдача/доставка |
| [Клуб](recipes/club.md) | Закрытое сообщество, инвайты, срок членства | Нет fail-open: неизвестное членство не даёт доступ | Инвайт → заявка/вход → активен → продление/истечение |
| [Публикации](recipes/publishing.md) | Черновик, согласование, расписание, права на чат | Права и target проверяются в момент отправки; approval привязан к версии | Черновик → preview → approval → отправка/расписание |

## Как читать рецепт

В каждом файле одинаковый каркас:

1. **Когда брать и когда не брать** — границы домена, чтобы не добавлять лишние сущности.
2. **Вопросы, меняющие сценарий** — то, что нельзя угадать из текста; только существенные развилки.
3. **Путь по экранам** — клиентский, операторский и административный маршрут.
4. **Роли и область объектов** — product-RBAC, ownership, tenant/chat scope. Статус в Telegram не равен роли продукта.
5. **Данные и инварианты** — реальные поля, ограничения и транзакционные проверки.
6. **Состояния и переходы** — допустимые и запрещённые изменения.
7. **Транзакции, повторы, идемпотентность** — где заканчивается доставка update и начинается бизнес-операция.
8. **Отказы и восстановление** — сеть, 403/429, stale, конфликт, повтор.
9. **Проверяемые сценарии** — что именно запустить и какое состояние увидеть.
10. **Опционально** — что добавлять только при подтверждённой потребности.
11. **Официальные источники** — точка проверки перед кодом.

Не копируй таблицы ролей и состояния буквально. Если в продукте нет операторов, оплат или согласования, соответствующая часть должна исчезнуть, а не остаться пустым экраном.

## Общие инварианты

- **Callback — не полномочие.** Actor берётся из update, роль и scope — из серверного хранилища; объект и его текущее состояние проверяются заново.
- **Два уровня повторов.** `(bot_id, update_id)` защищает доставку; версия объекта, одноразовый токен или доменный idempotency key защищает смысл операции при новом update id.
- **Один commit — одна бизнес-операция.** Нельзя сначала пометить update/действие выполненным, а потом менять объект. Для быстрых DB-операций dedup, изменение и завершение должны быть в одной транзакции.
- **DB и Telegram не атомарны.** Уведомление/отправку восстанавливай через outbox с lease; exactly-once доставку не обещай. Источник истины — БД и стабильный экран статуса.
- **Время.** Храни UTC instant и IANA timezone для правил/отображения. Не угадывай пояс по языку; проверяй DST gap/fold. Для сроков/напоминаний — durable jobs с дедупликацией.
- **Деньги.** Цена, валюта и сумма — серверные. Уникальность charge id и entitlement проверяется constraint-ом; «Я оплатил» не является оплатой.
- **Доступ.** Owner задаётся доверенным конфигом, не первым `/start`. Проверка `getChatMember` может быть недоступна/устареть; ошибка не превращается в разрешение. Скрытое меню не защита.
- **Приватность.** Внутренние заметки, чужие объекты и секреты не должны попадать в тот же renderer/outbox, что клиентский текст. Удаление/экспорт/срок хранения — по задаче.
- **Опциональность.** Redis, очередь, Mini App, платежи, напоминания, мультитенантность, отдельная веб-админка добавляются только при реальной потребности; текущий стек сохраняется.

## Выбор по задаче

- **Нужно выбрать время/ресурс и не пересечься** → booking. Если продаёшь только билеты без слотов, ближе shop.
- **Нужна переписка с историей, статусами и оператором** → support. Если только FAQ, не создавай тикеты.
- **Нужно взять деньги и выдать товар/доступ** → shop. Если оплата офлайн и товар физический, проверь общий Payments, а не Stars.
- **Нужно ограничить вход и поддерживать членство** → club. Если это просто публичный канал, не добавляй инвайты.
- **Нужно согласовать и опубликовать материал** → publishing. Если пользователь сам пишет пост в клиенте, не строй publishing-backend.

## Общий формат проверки

Каждый сценарий оформляй как integration test в текущем стеке:

- реальная тестовая БД с миграциями, а не один mock-connection;
- для гонок — две независимые транзакции/два worker-а; фиксированное UTC-время;
- для Telegram-побочных эффектов — fake/outbox transport с проверкой payload, без живой публикации;
- assertion на наблюдаемое состояние и constraint/audit, не на число вызовов внутренней функции;
- для UI — доступность действия и текущий экран после stale/повтора;
- живой Telegram-клиент проверяется отдельно, с разрешённым тестовым ботом и чатом.
