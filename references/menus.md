# Меню, кнопки и диалоги

## Выбор компонента

| Компонент | Используй для | Не путай с |
|---|---|---|
| Command menu (`setMyCommands`) | `/start`, `/help`, `/menu`, `/cancel`, при наличии `/settings` | Серверной проверкой прав: scope скрывает команду, но не запрещает её отправить |
| Inline keyboard | Действие над карточкой, страницы, выбор/подтверждение, настройки | Reply keyboard: callback не посылает обычный текст в чат |
| Reply keyboard | Несколько часто используемых верхних разделов, нативный запрос контакта/локации | Безопасной формой: такой же текст может быть введён вручную |
| `ForceReply` | Направленный ответ на вопрос, особенно с privacy mode в группе | Персональной тайной перепиской |
| Rich inline button/row | CTA рядом с соответствующим разделом rich-поста | Произвольным JS или обычным HTML button |
| Menu button | Список команд или запуск Mini App | Клавиатурой под конкретным сообщением |
| Mini App | Длинная форма, календарь, сложный каталог | Обязательным дополнением любого бота |

Inline-кнопка содержит ровно один тип действия помимо оформления/text. Нельзя одновременно `url` и `callback_data`. URL-кнопка не создаёт callback; если нужен учёт перехода, проектируй его отдельно по требованию. Условия `web_app`, платежной и login-кнопки проверь в [официальной схеме](https://core.telegram.org/bots/api/types/inlinekeyboardbutton.md). `pay` и `callback_game` имеют ограничения первой строки/позиции. Reply keyboard не поддерживается в каналах и business-сообщениях; не переноси UX из лички без проверки.

## Структура экрана

Для каждого экрана зафиксируй: id/родитель, цель, текст, строки кнопок, разрешённые роли, состояние/данные, действие/переход, пустое состояние и ошибка. Пример пользовательского пути:

```text
Главная
  [Создать заявку]
  [Мои заявки] [Помощь]
  [Настройки]
  [Управление] — только при серверном permission

Создать → Вопрос 1 → Вопрос 2 → Предпросмотр → Подтвердить → Результат
                         [Назад] [Отмена]
Мои заявки → Список страницами → Карточка → Доступные действия
Помощь → Правила / Связаться
Управление → Рабочая очередь / Пользователи / Настройки / Аудит
```

Это пример, не обязательные разделы для любого бота: подставь действия предметной области. Настройки без изменяемых параметров и фиктивная поддержка не нужны.

## Расстановка

- 3–6 понятных верхних разделов обычно достаточно; основное действие первым, второстепенные ниже.
- 1–2 кнопки в строке, 3 только для коротких равноправных вариантов. Это UX-рекомендация, не API-лимит.
- Подпись — конкретное действие («Подтвердить запись», «Изменить время»), не «Да» без контекста. Иконка необязательна и не заменяет текст.
- Сначала действия над объектом, затем пагинация, последней строкой «Назад»/«Главная». Опасное действие отдели от подтверждения и обозначь последствия текстом; цвет не единственный сигнал.
- «Назад» возвращает на предыдущий смысловой шаг и сохраняет допустимый ввод. «Отмена» завершает текущий ввод без применения и показывает стабильный экран. После commit отмена формы не отменяет операцию в БД.
- На экране результата покажи что произошло и куда идти дальше; не оставляй пользователя с одним «Успешно».
- Пустая очередь: «Заявок пока нет» + полезный переход. Для неподходящего ввода — ошибка у текущего шага и пример допустимого формата.

## Callback lifecycle

1. Быстро вызови `answerCallbackQuery` (в aiogram `query.answer()`), включая неизвестную/запрещённую/просроченную кнопку. Не заставляй клиент ждать БД, LLM или внешнего API. ACK означает приём нажатия, **не успех бизнес-операции**.
2. Разбери разрешённый формат callback. Лимит — 1–64 байта UTF-8, не символа. Пример: `req:confirm:42:3` (действие, id, версия); для длинного контекста — короткий непрозрачный серверный ключ.
3. Идентифицируй actor через `callback_query.from.id`; проверь права, объект, организацию/чат, срок/версию, текущий статус. Кнопка из пересланного/старого сообщения или подмена payload не дают права.
4. Выполни транзакционную бизнес-операцию, затем обнови экран из БД. Для долгой операции покажи принятый статус и итог отдельно.
5. Для stale/duplicate/conflict: понятный ответ + актуальная карточка/меню, без повторного действия и без утечки чужих данных. Удаление или disabled-кнопка улучшают UX, но не заменяют серверную защиту.

Не кодируй в callback токены, PII, цены как источник истины, роли или SQL. Подпись callback не отменяет RBAC/ownership. FSM state и callback version имеют разные задачи.

## Редактирование и формы

Редактируй существующую inline-карточку при навигации; новые сообщения уместны для финального результата, отдельного события и истории. Не делай весь бот вечным редактированием одного сообщения: пользователь может удалить его, Telegram может не позволить edit, callback может иметь `inline_message_id` вместо доступного `message`. Обработай `MaybeInaccessibleMessage`; для inline mode используй `inline_message_id`, а не несуществующий chat id.

В групповом сообщении не редактируй публичный текст в личную карточку пользователя — изменения увидят все. Используй личку или проверенный ephemeral API; `selective` у reply-клавиатуры не превращает сообщение в приватное.

FSM: один понятный вопрос на шаг, обязательность/валидация до перехода, preview перед commit; `/cancel` и `/menu` имеют явный приоритет над вводом. Разделяй сессии по bot/user/chat/topic при необходимости; настрой срок и восстановление. Для контакта проверь `contact.user_id`, если нужен именно номер отправителя; не считай пересланный контакт доказательством личности.

Пагинацию делай со стабильной сортировкой (например, created_at + id), фильтром и границами доступа на каждом запросе. При смене данных покажи актуальную страницу, а не неподтверждённый старый индекс. Для пользовательских языков вынеси тексты в принятый механизм i18n; callback ids от текста перевода не зависят.
