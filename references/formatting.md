# Форматирование Telegram: обычное и rich

Снимок проверен 2026-10-26 по [Bot API 10.3](https://core.telegram.org/bots/api-changelog.md). Перед применением новых полей сверяй [контракт метода](https://core.telegram.org/bots/api.md) и установленный SDK. Пользовательская статья — контекст UX, не схема HTTP.

## Выбери правильный рендерер

| Поверхность | Как передавать | Подходит для |
|---|---|---|
| Обычное сообщение | `sendMessage`, `text` + `parse_mode="HTML"`/`"MarkdownV2"` **или** `entities` | Короткая карточка, меню, уведомление; 1–4096 символов после разбора entities |
| Rich message | `sendRichMessage`, `rich_message` с ровно одним из `html`, `markdown`, `blocks` | Заголовки, настоящие таблицы, details, медиа между абзацами, формулы, длинный материал |
| Сообщение вручную в клиенте | Выделение текста/редактор Telegram; доступность зависит от версии/подписки | Пользовательский пост; копирование исходного HTML в поле чата само по себе не включает Bot API parser |
| Mini App | HTML/CSS в приложении, Telegram theme/safe areas | Сложные формы, календарь, интерактивные таблицы, не требуемые для простого меню |

`sendMessage(parse_mode="HTML")` не принимает `<h1>`, `<table>`, `<details>`, `<p>` или CSS. Rich HTML принимает поддерживаемые rich-теги, но не является произвольной веб-страницей. Rich Markdown использует `**bold**`, а MarkdownV2 — `*bold*`; не применяй один общий escaper ко всем режимам.

## Обычный текст

Предпочитай HTML для контролируемых коротких шаблонов. Экранируй **подставляемые значения**, не готовую разметку целиком. Поддерживаются `b/strong`, `i/em`, `u/ins`, `s/strike/del`, `a`, `code`, `pre`, `blockquote`, `blockquote expandable`, `tg-spoiler`/`span class="tg-spoiler"`, а также актуальные `tg-emoji` и `tg-time` с ограничениями из API. Перенос — `\n`, не `<br>`. Не вставляй произвольные теги из пользовательского или LLM-текста.

Пример тела POST к `sendMessage`; ID демонстрационный:

```json
{
  "chat_id": 123456789,
  "parse_mode": "HTML",
  "text": "<b>Заявка №42</b>\nСтатус: ожидает подтверждения\nКлиент: Анна &amp; Иван\n\nВыберите действие.",
  "reply_markup": {"inline_keyboard": [
    [{"text": "Подтвердить", "callback_data": "req:ok:42:v3"}],
    [{"text": "Назад", "callback_data": "nav:requests"}]
  ]}
}
```

MarkdownV2 вне code/link требует escaping набора ``_ * [ ] ( ) ~ ` > # + - = | { } . !`` и обратного слеша. В `code/pre` отдельно экранируй backtick и backslash; внутри URL — `)` и backslash. Используй готовый контекстный formatter SDK, а не цепочку случайных replace. Старый `Markdown` — legacy, не выбирай для нового проекта.

При ручных `MessageEntity` `offset`/`length` измеряются в **UTF-16 code units**, не в Python `len()` и не в UTF-8 байтах. Emoji вне BMP занимают две units; combining/ZWJ-последовательности могут состоять из нескольких code points. Используй entity builder SDK; не разрезай строку вместе с entities обычным слайсом.

## Rich messages

[Официальные правила](https://core.telegram.org/bots/api/rich-messages.md), [InputRichMessage](https://core.telegram.org/bots/api/types/inputrichmessage.md), [sendRichMessage](https://core.telegram.org/bots/api/methods/sendrichmessage.md).

Проверенные ограничения: до **32768 UTF-8 characters** текста (это не лимит UTF-8 байтов), включая alt custom emoji и исходник формул; до 500 блоков вместе с вложенными; 16 уровней вложения; 50 медиа; 20 колонок таблицы. У исходной сериализованной разметки и отображаемого текста разный размер; проверяй правила выбранного способа отправки, не используй байтовый счётчик как счётчик символов.

Пример тела POST к `sendRichMessage`:

```json
{
  "chat_id": 123456789,
  "rich_message": {
    "html": "<h2>Тарифы</h2><p>Выберите подходящий вариант.</p><table bordered striped compact><tr><th>План</th><th>Цена</th></tr><tr><td>Базовый</td><td>500 ₽</td></tr><tr><td>Команда</td><td>1500 ₽</td></tr></table><details><summary>Условия</summary><p>Расчёт за месяц. Перед оплатой покажем итог.</p></details><tg-button-row><tg-button type=\"callback_data\" style=\"primary\" data=\"plan:choose\">Выбрать тариф</tg-button></tg-button-row>"
  }
}
```

В `rich_message` не нужны `text` и `parse_mode`. Для материала на 12000 символов используй тот же rich-контракт и семантические блоки, не разбивай автоматически на сообщения по 4096. При превышении rich-лимитов дели по самостоятельным разделам с навигацией; не режь HTML/Markdown посередине тега или entity.

| Задача оформления | Rich HTML |
|---|---|
| Иерархия | `h1`…`h6`, `p`, `hr` |
| Список/чеклист | `ul`/`ol`/`li`; `input type="checkbox"` внутри li |
| Сравнение | `table`, `tr`, `th`, `td`, `caption`; inline formatting в ячейках |
| Дополнительные условия | `details` + `summary`; `open` только для раскрытого по умолчанию |
| Цитата | `blockquote`, `blockquote expandable`, `cite`; `aside` для pull quote |
| Формула/индекс | `tg-math`, `tg-math-block`, `sub`, `sup` |
| Навигация по тексту | `a name="section"` + `a href="#section"`; references для сносок |
| Медиа | Отдельные блоки `img`, `video`, `audio`, `tg-document`, figure/figcaption, collage/slideshow |
| Действие в тексте | `tg-button`, `tg-button-row`; тип `callback_data` использует атрибут `data`, не `callback_data` |

Rich `tg-button` поддерживает `danger/success/primary/link`; `link` — только callback. У `InlineKeyboardButton` проверяй его отдельную схему: в снимке разрешены `danger/success/primary`, не переноси `link` из rich-кнопки. Callback payload обоих видов — 1–64 **байта** UTF-8. Обычная и rich-кнопки отправляют callback, который нужно acknowledge через `answerCallbackQuery`.

Для URL-медиа используй доступный HTTPS-ресурс. Для ранее загруженного файла или multipart-загрузки используй `InputRichMessage.media` (`id` + `InputMedia...`) и `tg://photo?id=...`/`video`/`audio`/`document` по точной схеме; не придумывай замену URL на `file_id` в `src`. Права на отправку соответствующего медиа обязательны. SDK может отставать: обновляй совместимую зависимость, не подсовывай неизвестные поля, которые сериализатор молча отбросит.

## Куда что ставить

- Сверху — цель/результат и важный статус. Затем 1–3 коротких абзаца/поля, затем главное действие.
- Для короткого статуса достаточно обычного bold; для статьи используй настоящую иерархию rich-заголовков.
- Таблица — для сравнения нескольких значений, не для каждого абзаца; на мобильном обычно удобны 2–4 колонки. Длинный каталог — страницы/поиск.
- Основные цена, последствия и следующий шаг видны сразу. Юридические условия/подробности — в details, но не прячь критическую стоимость или отказ от возврата.
- Цитата — для чужой речи/выдержки; spoiler — скрываемое содержимое, не средство авторизации или защиты секрета.
- Code — для идентификатора/команды, не для выравнивания всего поста. Не рисуй псевдотаблицу пробелами, когда доступна настоящая.
- Обложка/медиа объясняют текст; CTA ставь рядом с нужным разделом или внизу, не дублируй его пять раз.
- Не печатай номер телефона, токен или приватную заявку в публичной группе ради красивой карточки.

## Перед отправкой

Проверь пустые/максимальные значения, `<>&`, кавычки, underscore, emoji/ZWJ, URL, длинную подпись, nesting и лимиты. Для rich отключай `skip_entity_detection` только осознанно; включай его, если ложное распознавание телефонов/команд мешает. При превью ссылки используй `link_preview_options` обычного сообщения по задаче. `protect_content` не гарантирует невозможность снимка экрана.

Уведомление `message is not modified` разбирай как конкретный ожидаемый результат только после сравнения актуального экрана; не подавляй все ошибки Telegram. Не маскируй неверную разметку отправкой plain text без согласованного поведения.
