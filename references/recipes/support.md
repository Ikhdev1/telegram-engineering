# Рецепт: поддержка

> Домен: обращения, очередь операторов, ответы и внутренние заметки. Не превращай FAQ-бота в тикет-систему, если нет переписки, назначения и истории.

## Когда брать

- Пользователь описывает проблему, получает ответ и видит историю обращения.
- Несколько обращений проходят через очередь, назначаются оператору и закрываются.
- Нужны внутренние заметки, невидимые клиенту, вложения или статусы ожидания.

**Не брать**, если достаточно статической справки или одного контактного адреса. Для продаж/слотов используй [shop.md](shop.md) или [booking.md](booking.md), а не тикет как универсальную сущность.

## Вопросы, меняющие сценарий

1. **Поверхность:** личка с ботом, группа/топик, комментарии канала или несколько каналов? Пользователь начал диалог сам? Бот не может писать произвольному человеку по username.
2. **Объект:** у клиента одно обращение или несколько? Нужны категории, приоритет, SLA, теги? Кто видит обращения других?
3. **Очередь:** общая, по навыку, по филиалу, по конкретному чату? Назначение вручную, «взять себе», автоназначение? Что если назначенный недоступен?
4. **Видимость переписки:** какие сообщения видны клиенту, какие только команде? Где хранятся вложения? Кто может экспортировать, сколько хранить?
5. **Жизненный цикл:** `new/open → pending_client ↔ pending_team → resolved → closed`? Кто закрывает, можно ли переоткрыть, когда авто-закрытие?
6. **Уведомления:** кого уведомлять о новом/просроченном обращении; как не дублировать; как учитывать 429/403 и тихие часы.
7. **Роли и tenant:** client, operator, admin, owner; несколько команд/ботов; нужен ли аудит и разграничение по чатам.
8. **Успех:** клиент получает ответ, обращение назначено, заметки не утекли, закрытие видно обеим сторонам.

## Путь по экранам

```text
Клиент
  Главное меню
    [Новое обращение] → тема → описание → предпросмотр → подтвердить → результат
    [Мои обращения] → фильтр/страницы → карточка → добавить сообщение / закрыть (по правилам)
  Ожидание ответа и закрытое обращение — разные экраны, не один «Успешно»

Оператор
  Очередь → фильтр (новые/мои/все/ожидают клиента) → карточка
    [Взять в работу] / [Переназначить] → публичный ответ / внутренняя заметка
    [Ожидает клиента] / [Решено] / [Закрыть] — разрешённые переходы
  Пустая очередь и отказ по роли различаются

Администратор / владелец
  Пользователи и роли → очередь и назначение → параметры (SLA/категории — если нужны) → аудит
```

В личке карточка не должна редактировать публичное сообщение в группе. Для персонального ответа в группе используй проверенный ephemeral-контракт; он не гарантирует доставку и не заменяет запись в БД. В форуме сохраняй `message_thread_id`; сообщение в общем чате и в теме не взаимозаменяемы.

## Роли и область объектов

| Действие | Клиент | Оператор | Администратор | Владелец |
|---|---|---|---|---|
| Создать обращение | Да | По правилам | В scope | В scope |
| Читать своё обращение | Да | Да | Да | Да |
| Читать чужое обращение | Нет | Только назначенное/очередь scope | В своём tenant/чате | В своём tenant |
| Публичный ответ | В своё обращение | В разрешённое | В scope | В scope |
| Внутренняя заметка | Нет | Да | Да | Да |
| Назначить исполнителя | Нет | Нет | Да, в scope | Да |
| Закрыть/переоткрыть | Своё — по правилам | Назначенное | В scope | В scope |
| Менять роли/настройки | Нет | Нет по умолчанию | Согласованный набор | Да |

Клиент, администратор Telegram-группы и оператор продукта — разные роли. Memberships/`getChatMember` не выдают автоматически доступ к тикетам. Если бот не администратор, `getChatMember` может быть недоступен; ошибка проверки — не разрешение. Для каждого запроса, включая поиск и счётчики, применяй tenant/chat scope.

## Данные и инварианты

Минимальная модель:

- `tickets`: id, tenant/team, requester_id, assignee_id (nullable), status, version, category, priority, subject, created_at, last_message_at, closed_at.
- `ticket_messages`: ticket_id, author_id, direction, visibility (`client` | `internal`), body, attachments, telegram_chat_id/message_id, created_at.
- `ticket_events`: actor, action, from/to status/assignee, reason, created_at (аудит).
- `attachments`: owner ticket, storage key, MIME/size, access scope, checksum; не публичный URL по умолчанию.

Инварианты:

- У обращения не больше одного текущего `assignee`; назначение/снятие фиксируется событием.
- `visibility` — обязательный enum, а не флаг в UI. Клиентский renderer и outbox выбирают **только `client`**; внутренняя заметка не должна попадать в тот же payload по ошибке.
- Статус меняется только по разрешённому переходу; old version/status отклоняется.
- Клиент видит свои объекты; оператор — только разрешённый scope. Отказ не раскрывает существование чужого тикета.
- Вложения имеют тот же scope, что тикет; проверка прав — на выдаче, а не только на ссылке.
- Внутренняя заметка может менять `last_message_at`/pending status по правилам, но не отправляется клиенту и не обязана увеличивать его unread.
- Секреты/токены/платёжные данные не попадают в тело тикета и аудит; вложения проверяются по размеру/типу.

## Состояния и переходы

| Из | В | Условие |
|---|---|---|
| `new` | `open`/`assigned` | Взят в работу или назначен |
| `open` | `pending_client` | Отправлен публичный ответ, ждём клиента |
| `pending_client` | `pending_team`/`open` | Клиент ответил или команда вернула в работу |
| `open`/`pending_team` | `resolved` | Проблема решена; публичное объяснение |
| `resolved` | `closed` | Истёк срок или оператор закрыл; правило задано |
| `closed`/`resolved` | `reopened`/`open` | Разрешённое переоткрытие; версия +1 |
| любой активный | `spam`/`cancelled` | Только по явной политике и с аудитом |

Запрещено: закрывать без записи результата, если это требуется политикой; менять assignee без аудита; переоткрывать закрытый тикет старым callback без проверки версии. Внутренняя заметка не должна сама переводить тикет в «ожидает клиента».

## Транзакции, повторы и идемпотентность

- **Приём обращения.** В одной транзакции: dedup `(bot_id, update_id)`, создание ticket + первого сообщения, audit, outbox уведомления. Отдельный commit «update обработан» до создания — потеря работы.
- **Назначение.** Атомарный claim: `UPDATE ... SET assignee=:me, version=version+1 WHERE id=? AND assignee IS NULL AND status='new'` или строка с блокировкой. Два оператора: ровно один получает назначение; второй видит актуального исполнителя.
- **Ответ.** Публичный ответ: вставить сообщение `client`, изменить статус, поставить доставку в outbox — в одной транзакции. Внутренняя заметка: только запись `internal` + audit; никакого клиентского outbox.
- **Доставка.** Telegram send не атомарен с БД; outbox worker с lease и сохранением outcome. Повтор может дать дубль; exactly-once не обещай. В тексте — стабильный номер обращения, а не «доставлено гарантированно».
- **Двойной клик/новый update id.** Версия тикета и idempotency key на действие; второй ответ не создаёт второй публичный ответ. Быстрый `answerCallbackQuery` — ACK, не успех.
- **Старые кнопки.** Перед каждым переходом загрузи актуальные actor/assignee/status/version; для admin-операций перепроверь scope. Отзыв роли влияет на уже отправленные кнопки.
- **Ephemeral.** Если показываешь приватную карточку в группе, `ephemeral_message_parameters` не является хранилищем; результат и подтверждение пиши в БД. `selective` reply keyboard не делает сообщение приватным.

## Частые ошибки и отказы

- Внутренняя заметка попадает в клиентский outbox или в общий renderer — критическая утечка.
- Публичный ответ уходит не в тот чат/топик; `message_thread_id` потерян.
- В группе редактируют общее сообщение в личное меню; другой участник видит изменение.
- Два оператора одновременно назначают себя; двойной ответ/аудит.
- Оператор без scope читает чужой тикет по номеру или старой ссылке.
- Закрытие по кнопке без текущей версии; stale-переход воскрешает обращение.
- Клиент отвечает после закрытия; система молча создаёт новый тикет или теряет ответ — выбери и покажи правило.
- Вложение отдаётся по публичному URL/без проверки scope.
- `getChatMember` вернул ошибку, и код разрешил доступ «на всякий случай». Ошибка → запрет/ограничение.
- Бот заблокирован/не может писать; 403 показывается как «ответ отправлен».
- 429/лимиты: бесконечный retry, дубли, отсутствие `retry_after`.
- Эфемерное сообщение считают доказательством доставки или журналом.
- PII/секреты в аудите и логах; нет срока хранения.

## Проверяемые сценарии

1. **Два оператора берут обращение.** Две независимые транзакции одновременно вызывают «взять». Ожидаемо: одна назначенная запись, один audit, второй получает актуального исполнителя/конфликт; версия увеличилась ровно на 1.
2. **Внутренняя заметка не утекает.** Создать тикет, добавить `internal` note. Проверить клиентский render payload и outbox: заметки нет; публичный ответ присутствует. Проверить, что счётчик клиентских unread не изменился, если такова политика.
3. **Чужой объект.** Клиент A открывает тикет B: нет данных и нет side effect; оператор вне scope получает отказ. Ответ не раскрывает существование B.
4. **Повтор update.** Один `(bot_id, update_id)` обработан дважды: один тикет/сообщение; второй вызов не создаёт дубль.
5. **Повтор с новым update id.** Один idempotency key публичного ответа, два нажатия: один публичный ответ, второй возвращает сохранённый результат.
6. **Отзыв роли и старая кнопка.** Выдать оператору доступ, открыть карточку, отозвать роль, нажать старую кнопку. Ожидаемо: отказ, без ответа/смены статуса.
7. **Stale-закрытие.** Закрыть тикет; старый callback «Закрыть» с версией v1 не меняет состояние; показывается актуальная карточка.
8. **Тема форума.** Ответ из тикета, привязанного к теме A, не попадает в общий чат/тему B; `message_thread_id` сохранён.
9. **Ошибка проверки членства.** `getChatMember` таймаутит/403; privileged action запрещено или ограничено, в аудите причина. Нет fail-open.
10. **Пустая очередь.** Новых обращений нет: пустой экран с полезным переходом, без фальшивых счетчиков и без «ошибки».
11. **Доставка.** Outbox worker падает между send и записью результата; после рестарта возможен дубль по выбранной политике, но БД не теряет ответ; статус различает `sending`/`sent`/`unknown`.
12. **Вложение.** Пользователь без доступа к тикету не получает файл; проверка на выдаче, не только скрытая ссылка.

## Опционально и условно

- **SLA/просрочки** — только если есть обязательство и таймер; durable jobs + дедуп.
- **Теги, canned responses, CSAT, база знаний, автоответы/LLM** — отдельные функции; LLM не должна получать чужие данные/секреты без согласованной политики.
- **Несколько команд/tenant, отдельная веб-админка, Mini App** — при реальной сложности; сохрани текущий стек и серверную auth.
- **Вложения/антивирус/экспорт** — по требованиям; не добавляй публичные ссылки.
- **Ephemeral UI в группе** — только если нужен персональный ответ при наличии ограничений доставки; не заменяет личку/БД.
- **Очередь/Redis** — только при подтверждённой потребности в фоне/нагрузке; транзакции БД не заменяются.
