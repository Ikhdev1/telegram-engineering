# Рецепт: магазин

> Домен: продажа цифрового товара/услуги за Telegram Stars или физического товара через платёжного провайдера. Это рецепт, а не готовый магазин; сохраняй выбранный стек и проверяй платёжные правила перед запуском.

## Когда брать

- Есть каталог, цена, заказ, оплата и выдача товара/доступа.
- Нужно различать цифровой товар (доступ, файл, подписка) и физический заказ (адрес, доставка).
- Нужны история заказов, повторная оплата, возврат или поддержка платежа.

**Не брать** для простого списка цен без оплаты. Для записи на услугу со слотами используй [booking.md](booking.md); для контента без продажи — [publishing.md](publishing.md).

## Вопросы, меняющие сценарий

1. **Тип товара:** цифровой товар/услуга внутри Telegram или физический товар/офлайн-услуга? От этого зависят Stars, `provider_token`, адрес и доставка.
2. **Валюта/регион:** где продаётся, какие валюты/провайдеры доступны, есть ли налоги/сборы, возрастные ограничения.
3. **Ассортимент:** варианты, количество, остатки, резерв, срок жизни резерва; может ли товар закончиться после выставления счёта?
4. **Счёт:** один-к-одному в личке, в группе/канале, inline, пересылаемый? Кто может оплатить? Какой `start_parameter`: пустой оставляет Pay на пересланных копиях (могут платить разные пользователи); непустой заменяет Pay на URL-кнопку с deep link. **В API нет флага «одноразовый счёт».** По официальной странице Payments single-chat invoice в личке с ботом оплачивается один раз, а в другом чате может быть оплачен многими; политику повторных charge/order всё равно определяет сервер.
5. **Выдача:** мгновенный доступ/файл/подписка или физическая доставка? Как подтверждается получение? Что при повторной выдаче?
6. **Возвраты/споры:** кто одобряет refund, в каком окне, как учитывается chargeback, что делать при частичной выдаче.
7. **Роли:** покупатель, поддержка, оператор выдачи, админ каталога, владелец; кто видит адрес и платёжные данные.
8. **Успех:** оплата подтверждена сервером, заказ в состоянии `paid`, выдача/доставка создана один раз, сумма/валюта совпали с заказом.

## Путь по экранам

```text
Покупатель
  Каталог → Карточка товара → Вариант/количество → Проверка заказа
    сумма, валюта, доставка/срок, правила возврата
  [Оплатить] → счёт Telegram → pending → успешная оплата → выдача/доставка → результат
  [Мои заказы] → карточка → статус/повторная выдача/запрос возврата
  Пусто, ошибка загрузки, цена изменилась, нет в наличии — разные состояния

Поддержка / выдача
  Очередь заказов → карточка → выдать доступ / передать в доставку / возврат (если разрешено)
  Внутренняя заметка не видна покупателю

Администратор / владелец
  Товары, варианты, цены, остатки, правила возврата, аудит; секреты провайдера не в сообщениях
```

Перед счётом покажи итог: товар, вариант, количество, цена, валюта, доставка/срок, правила возврата. После оплаты покажи стабильный номер заказа и следующий шаг. Не оставляй один «Успешно» без того, что именно выдано.

## Роли и область объектов

| Действие | Покупатель | Поддержка | Оператор выдачи | Администратор | Владелец |
|---|---|---|---|---|---|
| Видеть свой заказ | Да | По обращению | По заказу | В scope | В scope |
| Видеть чужие заказы | Нет | Только нужные поля | Только назначенные | В tenant | В tenant |
| Создать счёт | Да | По правилам | Нет | Да | Да |
| Выдать цифровой доступ | Нет | Нет | Да, после `paid` | Да | Да |
| Оформить физическую доставку | Нет | Нет | Да | Да | Да |
| Сделать возврат | Запросить | Нет | Нет по умолчанию | Отдельное permission + подтверждение | Да |
| Менять цены/остатки | Нет | Нет | Нет | Да | Да |

Платёжные данные (полный адрес, телефон, provider charge id) показывай только тем, кому они нужны для операции. Секреты провайдера и токен бота не выводятся в админке. Покупатель не становится оператором из-за оплаты; доступ к заказу проверяется по owner/tenant.

## Данные и инварианты

Минимальная модель:

- `products` + `product_versions`: name, description, active, version; цена не должна быть UI-константой.
- `variants`/`inventory`: SKU, price, currency, stock, reserved, version.
- `orders`: id, buyer_id, tenant, status, currency, total_amount, price_version, delivery_type, address/contact (nullable), created_at, version, idempotency_key.
- `order_items`: product/variant, quantity, unit price snapshot, total.
- `payments`: order_id, `payer_user_id` (sender `from.id` сообщения с `successful_payment`), provider (`stars`/other), currency, amount, invoice_payload, `telegram_payment_charge_id` (unique), `provider_payment_charge_id`, status, paid_at.
- `entitlements`: order_id, product/variant, `user_id` (по политике — payer или bound buyer), status, granted_at; уникальность по заказу/позиции.
- `refunds`: payment_id, amount, reason, provider_ref, status, actor, timestamps.
- `shipments`: order_id, address, carrier/tracking, status (для физического заказа).

Инварианты:

- Цена, валюта и сумма — серверные. Callback/сообщение пользователя не меняют цену заказа.
- `total_amount` — целое в минимальных единицах валюты; не float. Для цифрового товара внутри Telegram — `XTR` (Telegram Stars). Для физического товара — валюта/провайдер по актуальным правилам Payments.
- Для `XTR` в `prices` должен быть **ровно один** `LabeledPrice` с полной серверной суммой; разбивка на строки/скидки/налоги остаётся в заказе и человекочитаемом описании, не в нескольких `prices`. Несколько компонентов допустимы для провайдерского/физического счёта, если это поддерживает провайдер.
- Плательщик определяется sender-ом (`from.id`) update с `successful_payment`, а не только `orders.buyer_id`. Для пересылаемого/группового счёта политика явная: один заказ на payer, либо `pre_checkout_query.from.id` должен совпасть с привязанным покупателем; иначе отказ. Если sender отсутствует или не совпадает с политикой — не выдавай автоматически, отправь в ручной разбор. `entitlement` и refund используют фактического payer-а, а не «предполагаемого» владельца.
- Один заказ не получает вторую успешную оплату как отдельную выдачу: повторный charge id идемпотентен; две разные оплаты одного заказа требуют явной политики (вторая — к возврату/ручной разбор).
- `telegram_payment_charge_id` уникален; сохраняется для возврата.
- Цифровая выдача/entitlement создаётся **только** после проверенного `successful_payment` и только один раз.
- Физический заказ не «выдаётся» как цифровой доступ; адрес/доставка — отдельные данные и права.
- Остаток не становится отрицательным; резерв освобождается по TTL/отмене; оплата при отсутствии товара требует явного возврата/альтернативы.
- Pre-checkout проверяет заказ, сумму, валюту и доступность; не подтверждает оплату, которой ещё нет.
- Invoice payload — непрозрачный серверный идентификатор, не цена/роль/секрет. Не клади туда PII.

Официально для цифровых товаров/услуг внутри Telegram используется **Telegram Stars** (`XTR`); `provider_token` для цифрового счёта можно оставить пустым. Физические товары/услуги идут через общий Payments с провайдером. Перед запуском проверь [актуальную страницу Stars](https://core.telegram.org/bots/payments-stars.md) и [Payments](https://core.telegram.org/bots/payments.md): правила и доступность могут меняться.

## Состояния и переходы

| Из | В | Условие |
|---|---|---|
| `draft` | `invoice_pending` | Заказ и цена зафиксированы, счёт создан |
| `invoice_pending` | `awaiting_payment` | Счёт отправлен; ждём pre-checkout/payment |
| `invoice_pending`/`awaiting_payment` | `cancelled`/`expired` | TTL, отмена, отказ pre-checkout |
| `awaiting_payment` | `paid` | Проверенный `successful_payment` совпал с заказом |
| `paid` | `fulfilling`/`shipped` | Выдача/передача в доставку начата |
| `fulfilling` | `fulfilled`/`delivered` | Выдача подтверждена; для физического — доставка |
| `paid`/`fulfilled` | `refund_pending` → `refunded` / `failed` / `manual_review` | Разрешённый возврат; подтверждённый результат провайдера или сверка |
| любой | `disputed`/`manual_review` | Chargeback/неоднозначная оплата |

Запрещено: `invoice_pending → fulfilled` без `successful_payment`; `refunded → fulfilled` без нового платежа; повторная выдача по тому же заказу; `paid` без проверки суммы/валюты/charge id.

## Транзакции, повторы и идемпотентность

- **Создание заказа.** Idempotency key от действия/клиента (не от цены в callback), фиксация price version и количества; при повторе возвращай тот же заказ, не создавай второй.
- **Резерв.** Атомарно уменьшить доступный остаток/создать резерв с TTL. Не держи БД-транзакцию во время сетевого вызова Telegram.
- **Pre-checkout.** Ответить быстро, в пределах **10 секунд** по официальной инструкции. Проверь `invoice_payload`, заказ, сумму, валюту, наличие; дополнительно `pre_checkout_query.from.id` по политике счёта: связанный покупатель или допустимый отдельный payer. При ошибке откажи с понятным текстом. Pre-checkout не доказывает оплату.
- **Success.** В одной транзакции: найти заказ, проверить `currency`, `total_amount`, `invoice_payload`, `payer_user_id` из sender-а сообщения, уникальность `telegram_payment_charge_id`, статус; записать payment с payer-ом, перевести `paid`, создать entitlement/outbox выдачи, audit. Повтор с тем же charge id возвращает существующий результат, не создаёт вторую выдачу; payer не подменяется на `buyer_id`.
- **Две оплаты и разные payer.** Если счёт пересылаемый/многоразовый, каждый charge может принадлежать другому payer-у. Политика явная: один заказ на payer (gift) либо только первый charge, второй — к возврату/разбору; либо `pre_checkout` отклоняет несовпавшего payer-а. Не выдавай дважды и не смешивай entitlement разных payer-ов.
- **Выдача.** Цифровой доступ — идемпотентная операция с уникальным `(order_id, item)`; повторный `successful_payment` или рестарт worker-а не дублирует. Физическая доставка — отдельный процесс и статус.
- **Возврат.** `refundStarPayment` (`user_id` фактического payer-а + `telegram_payment_charge_id`; отдельного idempotency-key в снимке нет) или provider refund — внешний side effect. Сначала `refund_pending`, затем вызов. Таймаут не означает успех или неудачу: сверь через `getStarTransactions` (id/направление/получатель транзакции и исходный charge id; для провайдера — его transaction/refund lookup). Подтверждённый существующий refund → `refunded`; явный отказ → `failed`; неизвестно → `refund_pending`/`needs_review`. Повтор — только после сверки, иначе возможен второй возврат.
- **Уведомления.** Outbox и retry с `retry_after`; exactly-once доставку не обещай. Заказ и выдача в БД важнее сообщения.

## Частые ошибки

- Подтверждение оплаты по кнопке «Я оплатил», redirect или сообщению пользователя.
- Выдача до `successful_payment` или после `pre_checkout_query`, но без фактической оплаты.
- Цена/валюта берутся из callback или текста; сумма не сверяется с заказом.
- Счёт на другую сумму/валюту; `start_parameter` считают флагом «одноразовый»; пересланный счёт оплачивает второй пользователь, а код кредитует исходного buyer-а.
- Для `XTR` отправлено несколько `prices`/tax/delivery строк вместо одного `LabeledPrice` с полной суммой — Telegram отклонит счёт.
- Двойная выдача при повторном update/рестарте; нет уникальности charge id/entitlement.
- Возврат помечен выполненным до ответа провайдера; повторный возврат без сверки; refund отправлен не фактическому payer-у.
- Физический заказ продаётся как цифровой (или наоборот); Stars применяются к офлайн-услуге без проверки правил.
- Остаток ушёл в минус из-за гонки; оплата при отсутствии товара без возврата.
- Pre-checkout отвечает дольше 10 секунд или ходит в медленный сервис.
- Адрес/телефон/charge id видны всем операторам/в логах; invoice payload содержит PII.
- Бот не отвечает на `/paysupport`/не даёт поддержку (требование для Stars по официальной странице).
- 403/429 в уведомлении трактуются как отмена оплаты.

## Проверяемые сценарии

1. **Нет оплаты — нет выдачи.** Создать заказ, не присылать `successful_payment`; вызвать выдачу/закрытие: ожидаемо отказ, entitlement отсутствует.
2. **Pre-checkout с устаревшей ценой.** Изменить цену/остаток после счёта, затем pre-checkout: ожидаемо отказ, заказ не `paid`, текст причины человеку.
3. **Pre-checkout с неверной валютой/суммой.** Ожидаемо отказ; нет `paid`/entitlement.
4. **Успешная оплата.** Проверенный `successful_payment` с правильным payload/amount/currency: заказ `paid`, одна запись payment, один entitlement; audit.
5. **Повтор charge id.** Доставить тот же `successful_payment` дважды: один paid/entitlement, второй возвращает существующий результат.
6. **Две разные оплаты одного заказа.** Ожидаемо: одна принята, вторая помечена к возврату/разбору; нет двойной выдачи. Политика проверяется тестом.
7. **Stars-счёт.** Для цифрового счёта: `currency="XTR"`, пустой `provider_token` (по текущей инструкции), сумма целая, `prices.length == 1` и её amount равен серверному total. Разбивка на позиции/налог/скидку хранится в заказе, а не в нескольких `prices`. Для физического заказа: провайдер/валюта по Payments, допустимые компоненты и адрес/доставка обязательны.
8. **Последний товар.** Две конкурентные покупки при остатке 1: один `paid`/fulfilled, второй получает «нет в наличии»/возврат; остаток не отрицательный.
9. **Возврат и неоднозначный таймаут.** Разрешённый возврат вызывает `refundStarPayment` с `user_id` фактического payer-а и charge id; provider ack → `refunded` + audit. Смоделировать: refund фактически прошёл, транспорт вернул timeout → сверка через `getStarTransactions`/provider lookup переводит в `refunded` без второго возврата. Явный отказ → `failed`/`refund_pending`; повтор после подтверждённого refund не создаёт второй возврат. Не требовать «ровно один вызов провайдера» при неизвестном результате.
10. **Чужой заказ.** Другой пользователь не видит детали/адрес; подделанный callback не создаёт выдачу/возврат.
11. **`start_parameter` и пересылка.** Пустой `start_parameter`: у пересланной копии остаётся Pay (могут платить разные пользователи); непустой: у пересланной копии URL/deep link вместо Pay. Для single-chat invoice по официальной странице: в личке с ботом — один успешный платёж, в другом чате — несколько плательщиков; сервер либо создаёт отдельные charge/order, либо отклоняет по политике. Проверить payload и что второй payer не перезаписывает заказ/entitlement. Одноразовость не выводится из `start_parameter`.
12. **Pre-checkout latency.** Ответ не превышает 10 секунд; медленная проверка не блокирует подтверждение до истечения окна.
13. **Другой payer по пересланному счёту.** Заказ принадлежит A; forwarded invoice оплачивает B. Ожидаемо: `payments.payer_user_id=B`; entitlement/refund по явной политике (B или отказ/новая order), A не получает второй `paid`/entitlement; refund использует B + charge id.

## Опционально и условно

- **Физическая доставка**: адрес, shipping options, tracking; добавляй только для физического товара. Не показывай цифровой доступ как замену доставке.
- **Подписки/рекуррентные платежи**: проверь текущую поддержку и поля; не выдумывай автопродление для Stars.
- **Промокоды, мультивалютность, партнёрские выплаты, аналитика** — отдельные правила, тесты и налоги; не добавляй «на всякий случай».
- **Mini App/веб-магазин** — только при сложном каталоге; серверная проверка `initData`, не клиентский user_id.
- **Очередь/outbox** — при необходимости переживать рестарт и доставлять выдачу; не заменяй ими проверку оплаты.
- **Платные рассылки/реклама** — отдельный бюджет и актуальные правила; не включай автоматически.
