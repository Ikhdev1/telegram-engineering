# Рецепт: публикации

> Домен: подготовка, предпросмотр, согласование и отправка поста в конкретный канал/группу. Это рецепт, а не готовый редактор. Сохраняй существующий стек; не строй publishing-backend, если достаточно ручной публикации.

## Когда брать

- Материал готовит один человек, согласует другой, публикует третий (или те же роли, но с разными permission).
- Нужны черновик, предпросмотр, расписание, история версий и точный target.
- Публикация идёт в канал, группу/тему или несколько чатов с разными правами.

**Не брать**, если пользователь просто оформляет текст и публикует его сам в клиенте; верни готовый текст и инструкцию. Для инвайтов/членства — [club.md](club.md); для продажи контента — [shop.md](shop.md).

## Вопросы, меняющие сценарий

1. **Target:** канал, группа, тема форума, community, несколько чатов? Бот администратор именно там? Нужны ли разные тексты для разных чатов?
2. **Роли:** кто автор, согласующий, публикатор? Сколько согласований? Может ли автор публиковать сразу?
3. **Черновик:** где живёт, кто видит, сколько версий/вложений хранить? Нужен ли общий доступ команды?
4. **Согласование:** approval привязан к конкретной версии и target? Что происходит после правки, смены target или расписания? Кто может отозвать approval?
5. **Расписание:** немедленная отправка или будущая? В какой IANA timezone задаётся локальное время, что при DST gap/fold? Можно ли отменить/перенести после постановки в очередь?
6. **Контент:** обычное сообщение или rich? Заголовки/таблицы/details/медиа/CTA? Нужен ли web preview, комментарии, cross-post, direct messages канала?
7. **Права:** кто может публиковать/редактировать/удалять в каждом чате; что делать при потере админ-прав; как проверять forum topic.
8. **Успех:** материал ушёл ровно в разрешённые target-ы; по каждому target сохранены свой status/message id, аудит и отсутствие дубля.

## Путь по экранам

```text
Автор
  Новый пост → target → текст/rich-контент → preview
    [Сохранить черновик] [Отправить на согласование]
  Черновики → карточка → редактировать/удалить/история версий

Согласующий
  Очередь согласований → diff/preview + target + версия
    [Одобрить] [Отклонить с причиной]
  Решение привязано к версии; правка после approval требует нового решения

Публикатор
  Одобренные → [Опубликовать сейчас] / [Запланировать]
    результат: sending → sent / failed / needs_review
  Запланированные → [Отменить] [Перенести] (с проверкой permission)

Администратор / владелец
  Каналы и права, шаблоны/расписание, аудит; секреты бота не в экране
```

Preview — это **предпросмотр данных**, а не доказательство клиентского рендера Telegram. Для rich-контента проверяй контракт и лимиты; для обычного — другой лимит и другой набор тегов. Не показывай «опубликовано», пока для каждого target не получен подтверждённый message id или выбранное состояние `needs_review`.

## Роли и область объектов

| Действие | Автор | Согласующий | Публикатор | Администратор | Владелец |
|---|---|---|---|---|---|
| Создать/редактировать свой черновик | Да | По scope | По scope | Да | Да |
| Видеть чужие черновики | Нет | В очереди scope | В scope | В tenant | В tenant |
| Одобрить | Нет | Да, в scope | Нет по умолчанию | Да, если право | Да |
| Публиковать в чат | Нет | Нет | Да, по per-chat праву | Да | Да |
| Менять target/шаблоны | Нет | Нет | Нет | В scope | Да |
| Удалять опубликованное | Нет | Нет | По праву | В scope | Да |

Права:

- **продукта** — автор/согласующий/публикатор/админ;
- **Telegram в конкретном чате** — бот админ и `can_post_messages`/`can_edit_messages`/`can_delete_messages` (для канала) или соответствующие права группы;
- **target** — точный chat id/тема, не «канал, который был раньше».

Право «подготовить текст» не означает право публикации. Публичный пост видят все; роль зрителя не меняет контент. Владелец тоже не обходит проверку target/permission.

## Данные и инварианты

Минимальная модель:

- `posts`: id, tenant, author_id, format (`message`/`rich`), content, content_hash, status (aggregate), version, created_at. Для multi-target это контейнер; target/message id здесь не авторитетны.
- `post_targets`: post_id, chat_id, topic, per-target status/outcome, rights snapshot, `published_message_id`, sent_at, version; **авторитетный источник** для multi-target и edit/delete.
- `post_versions`: снимок контента/вложений; правка создаёт новую версию.
- `approvals`: post_version_id, target, actor, decision, reason, expires_at, consumed_at, consumed_by_job_id, one-time token.
- `publish_jobs`: post_version_id, target, scheduled_at_utc, timezone, lease/status/attempts; один active job на пару, история статусов сохраняется.
- `post_events`: author/approver/publisher, action, target, outcome, timestamp, correlation.

Инварианты:

- Approval привязан к **content_hash + target + version** и действует до `expires_at`. Он расходуется один раз и только вместе с конкретным publish job; изменение текста/медиа/target инвалидирует approval (или требует явного re-approval по политике).
- Публикация разрешена только для approved/authorized версии, целевого target и unexpired/unconsumed approval.
- Для `(post_version, target)` — не больше одной **активной** job (`scheduled`/`sending`) через partial unique index. Отдельный terminal guard: не больше одного `sent` результата на пару (partial unique `WHERE status='sent'` или эквивалентная атомарная проверка). Иначе reschedule упирается в unique, а повтор после sent создаёт второй пост.
- `scheduled_at_utc` в будущем; локальное время хранится с IANA zone. DST gap/fold обрабатывается явно. Расписание не позже срока approval, если политика не требует отдельного продления.
- Permissions проверяются **в момент отправки**, а не только при создании черновика/расписания.
- Target topic: для форума `message_thread_id`, для direct messages канала — актуальное поле темы по контракту; не подменяй одно другим.
- Rich и обычное сообщение — разные поля/контракты. Не отправляй `<table>`/`details` через `parse_mode=HTML` обычного сообщения и не добавляй `text`/`parse_mode` в `rich_message`.
- Ответ Telegram не гарантирует exactly-once. После неоднозначного таймаута статус — `needs_review`, а не слепой повтор.
- `published_message_id`/target/status хранятся **на каждый target** (`post_targets`); top-level aggregate не используется для edit/delete multi-target. Права на edit/delete проверяются отдельно для каждого target.

## Состояния и переходы

| Из | В | Условие |
|---|---|---|
| `draft` | `previewed` | Валидация контента и target |
| `previewed` | `pending_approval` | Политика требует approval |
| `pending_approval` | `approved` / `rejected` | Решение по конкретной версии |
| `approved` | `scheduled` / `sending` | Approval unexpired/unconsumed, версия/target совпадают; target/permission актуальны |
| `scheduled` | `sending` | Наступило время, job получил lease, approval всё ещё unexpired/unconsumed |
| `sending` | `sent` | Получен message id; сохранить его в `post_targets` вместе с target/version/временем |
| `sending` | `failed` / `needs_review` | Явный отказ / таймаут, side effect неизвестен |
| `scheduled`/`approved` | `cancelled` | Отмена до отправки; approval/audit обновлены |
| `sent` | `edited`/`deleted` | Отдельное право и новая версия/аудит |

Запрещено: `rejected → sent` без нового approval; `sending → scheduled` после таймаута без сверки; повторная отправка по тому же job без проверки статуса; edit после смены target без повторной проверки прав.

## Транзакции, повторы и идемпотентность

- **Черновик.** Сохраняй версию/`content_hash`; правка — compare-and-swap по version, иначе параллельные редакторы затирают друг друга.
- **Approval.** В одной транзакции: проверить актуальную версию/target, право согласующего, отсутствие более нового approval и `expires_at`; записать решение, срок и одноразовый токен. Правка после — инвалидирует. Approval нельзя использовать после `expires_at` или повторно.
- **Расписание.** Проверить unexpired/unconsumed approval и `scheduled_at <= approval.expires_at`; создать одну **активную** job (`scheduled`) в транзакции, сохранив старые job-ы в истории. Partial unique index на `(post_version, target)` для active statuses; reschedule сначала переводит старую job в `cancelled`, затем создаёт новую. Полный unique на всю пару не ставить. Планирование делает приложение; не выдумывай параметр расписания у метода отправки, сверяй контракт.
- **Отправка.** Перед вызовом Telegram заново проверь `getChatMember`/права бота и target. В той же транзакции, где job получает lease, повторно проверь у approval `expires_at > now`, `consumed_at IS NULL`, привязку к job/version/target и отсутствие `sent` для пары; атомарно пометь approval consumed и job `sending`. Если проверка неизвестна/ошибка — не публикуй (fail closed). Вызов Telegram — вне БД-транзакции; храни `sending` + lease.
- **Таймаут.** Side effect мог выполниться. Не повторяй автоматически; переведи в `needs_review` и сохрани неопределённость. Повторная отправка по тому же job/паре запрещена, пока не выполнена сверка. Exactly-once не обещай.
- **Несколько целей.** Отправляй по каждой цели отдельно; `post_targets` хранит собственные status и `published_message_id`. Один успех и один отказ не должны выглядеть как «всё опубликовано»; edit/delete адресуй конкретному target.
- **403/429.** 403 — потеря прав/blocked: остановить, отметить. 429 — `retry_after` и ограниченная политика; не бесконечный retry. Не маскируй ошибку «успехом».
- **Approval и ephemeral.** Если предпросмотр/подтверждение показывается приватно в группе, approval хранится в БД; ephemeral-сообщение не является аудитом и может не дойти. Не редактируй общее сообщение в личное.

## DST и расписание

- Пользователь задаёт локальное время в явной IANA zone; сохраняй UTC instant и zone.
- **Gap:** локальное время не существует — отклонить или перенести по документированной политике; не сдвигать молча.
- **Fold:** время встречается дважды — выбрать offset/fold явно или детерминированно; храни выбранный instant.
- После смены DST повторное расписание не должно пересчитываться «на глаз»; проверь тестом на фиксированных датах (например, `Europe/Berlin` 29.03.2026 и 25.10.2026; `America/New_York` — свои даты).
- Отмена/перенос расписания атомарны: старый job отменён/помечен stale, новый создан один раз. Перенос не должен оставить два активных job-а.

## Частые ошибки

- Approval на «текст вообще», а не на версию+target; после правки уходит неутверждённый текст.
- Approval истёк/уже consumed, а job всё равно публикует; повторный callback после sent создаёт второй пост.
- Один top-level message id для multi-target: edit/delete попадает не в тот чат; reschedule ломается о полный unique или оставляет две active job.
- Публикация в канал, где бот больше не админ; 403 трактуется как успех.
- Перепутаны `message_thread_id` темы и тема direct messages канала.
- Таблица/details отправлены обычным `sendMessage(parse_mode=HTML)`; видимого результата нет.
- Превышены rich-лимиты/вложенность; контент обрезан или отклонён.
- Расписание в локальной зоне сервера; DST gap/fold; задача срабатывает не в то время.
- Два worker-а отправили один пост; повтор после таймаута создал дубль.
- Старая кнопка «Опубликовать» после отзыва роли всё ещё работает.
- Ephemeral-подтверждение считают доказательством согласования/доставки.
- Preview выдают за реальный вид Telegram; нет проверки rich-лимитов/клиента.
- Удаление/редактирование опубликованного без проверки прав и аудита.
- CTA deep link с неверным/истёкшим payload; ссылка ведёт не туда.

## Проверяемые сценарии

1. **Автор не публикует.** Роль author/подготовка: кнопка публикации недоступна/сервер отклоняет; пост остаётся черновиком.
2. **Правка после approval.** Одобрить версию v1, изменить текст до v2; публикация v2 блокируется, approval инвалидирован; после нового approval проходит.
3. **Потеря прав.** Запланировать пост; убрать бота из админов/лишить `can_post_messages`; job при проверке перед отправкой не публикует, статус `failed`/`blocked`, аудит.
4. **Два worker-а.** Два процесса забирают один scheduled job: ровно один вызов отправки/один `sent` результат и message id; второй видит `sent`/не получает lease. Partial unique active job не мешает истории.
5. **Таймаут отправки.** Транспорт бросает timeout после возможной отправки: статус `needs_review`, автоматического второго поста нет; повторная отправка пары заблокирована до сверки.
6. **DST.** Запланировать на несуществующее локальное время (`Europe/Berlin` 29.03.2026 02:30) — отказ/явный перенос; на неоднозначное (25.10.2026 02:30) — выбранный offset/fold и корректный UTC.
7. **Rich.** Пост с таблицей/details уходит через `sendRichMessage`; в `payload` нет `text`/`parse_mode`, есть один `html`/`markdown`/`blocks`. Проверить лимиты до отправки.
8. **Форум/тема.** Пост для темы A не появляется в общем чате или теме B; сохранён правильный `message_thread_id`.
9. **Approval: expiry и повтор.** Approval с `expires_at` в прошлом нельзя запланировать; approval, истёкший между schedule и send, блокирует отправку (`needs_review`/`failed`, audit). Повторный approve по тому же токену не создаёт второй approval; после успешной отправки approval consumed и повтор не публикует.
10. **Старая кнопка.** Отозвать publish permission; нажать старую кнопку из сообщения: отказ без публикации.
11. **Частичный multi-target.** Один канал принял пост, второй вернул 403; `post_targets` хранит собственные status/`published_message_id`; успешный target можно отдельно edit/delete, у неуспешного message id отсутствует; UI не пишет «опубликовано везде».
12. **Ephemeral privacy.** Приватный preview/подтверждение не виден другому участнику; approval записан в БД; доставка ephemeral не считается гарантированной.
13. **Отмена расписания.** Отменить до отправки: job помечен `cancelled`, поста нет; после отмены старый callback не публикует.
14. **Публикация сейчас.** Approve + immediate publish: ровно один пост и message id; повторный publish-callback после `sent` не создаёт второй пост (sent guard + consumed approval).
15. **Reschedule.** Заменить scheduled job: ровно одна active job, старая остаётся `cancelled` в истории, unique violation нет. Если approval ещё валиден и не consumed, отправка проходит один раз; если истёк — нужна новая approval, отправки нет.

## Опционально и условно

- **Многоступенчатое согласование** — только если реально нужно; иначе один approval.
- **Мультиканальная публикация/кросс-пост** — отдельные target-статусы и права; не обещай атомарность.
- **Платные рассылки/реклама** — отдельный бюджет и актуальные правила; не включай без запроса.
- **Медиа-обработка/превью** — по требованиям; проверяй доступность HTTPS-медиа и права.
- **Комментарии/аналитика** — не обязательны; не добавляй сбор данных без задачи.
- **Mini App-редактор** — для сложного rich-контента; сервер проверяет `initData` и права.
