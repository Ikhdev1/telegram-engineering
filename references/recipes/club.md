# Рецепт: клуб

> Домен: закрытое сообщество с приглашениями, заявками, сроком членства и удалением по истечении. Это рецепт, а не готовый membership-бот. Сохраняй существующий стек и проверяй права бота в конкретном чате.

## Когда брать

- Доступ к чату/каналу/сообществу ограничен и управляется приглашениями или заявками.
- Членство имеет срок, источник, продление, истечение или ручное управление.
- Нужны роли модераторов/администраторов и аудит изменений доступа.

**Не брать**, если это публичный канал без ограничений или разовый платный доступ без членства. Для продажи доступа как товара см. [shop.md](shop.md); для публикаций — [publishing.md](publishing.md).

## Вопросы, меняющие сценарий

1. **Поверхность:** один чат/канал, несколько чатов, Telegram Community? Какие чаты видны участникам и кто может добавлять новые?
2. **Вход:** открытая ссылка, одноразовый инвайт, заявка с одобрением, allowlist, платная подписка? Кто создаёт и отзывает приглашения?
3. **Срок:** бессрочно, фиксированный период, подписка, ручное продление? Есть ли grace period, напоминание, автопродление?
4. **Истечение:** удалять из чата, снимать роль продукта, скрывать контент? Что происходит при повторном входе? Ban или kick?
5. **Права:** кто member/moderator/admin/owner; какие Telegram-права выданы боту (`can_invite_users`, `can_restrict_members`)? Кто может одобрять заявки?
6. **Приватность:** можно ли видеть список участников/инвайтов, сколько хранить, что логировать, кому доступен экспорт. Не попадают ли invite-токены в логи?
7. **Платно:** если да, какой источник оплаты/подписки, что при неуспешном продлении, возврате, chargeback; проверь актуальные правила Telegram для выбранного способа.
8. **Успех:** участник получает ровно один активный membership, срок соблюдается, неизвестное/ошибочное состояние не открывает доступ.

## Путь по экранам

```text
Пользователь
  Инвайт/deep link → [Вступить] → pending / active
    active → [Мой статус] → срок, продление, выход
    expired/removed → понятное объяснение, разрешённый путь возврата
  Ошибочный/использованный/истёкший инвайт — не «ошибка загрузки»

Администратор
  Участники → поиск по numeric ID/известному пользователю → членство и срок
    [Продлить] [Приостановить] [Удалить] — с подтверждением и аудитом
  Приглашения → создать (срок/лимит/заявка) → отозвать → история
  Заявки → одобрить/отклонить → результат

Владелец
  Политика членства, роли, несколько чатов/сообществ, аварийное восстановление
```

Не показывай список участников всем участникам, если это не согласовано. Ссылка-приглашение — не роль; её открытие не доказывает личность. Для персонального ответа в группе используй ephemeral-контракт, но membership/аудит храни в БД: доставка ephemeral не гарантируется.

## Роли и область объектов

| Действие | Участник | Модератор | Администратор | Владелец |
|---|---|---|---|---|
| Видеть свой статус | Да | Да | Да | Да |
| Видеть чужие сроки | Нет | В своём чате, по политике | В scope | В scope |
| Создать/отозвать инвайт | Нет | По праву | Да, в scope | Да |
| Одобрить заявку | Нет | По праву | Да | Да |
| Продлить/удалить | Нет | Нет по умолчанию | В scope + аудит | Да |
| Менять политику/роли | Нет | Нет | Ограниченный набор | Да |

Разделяй:

- **Telegram membership** (`creator/administrator/member/restricted/left/kicked`) — состояние в конкретном чате;
- **продуктовую роль** (member/moderator/admin/owner) — запись в БД;
- **права бота** в чате (`can_invite_users`, `can_restrict_members`, …), без которых операция невозможна.

Одно не выводится автоматически из другого. Администратор Telegram-чата не становится администратором продукта. Community объединяет чаты, но не выдаёт роли приложения; для каждого чата храни явный scope.

## Данные и инварианты

Минимальная модель:

- `memberships`: id, user_id, tenant/community_id, chat_id, status, starts_at, expires_at, source_invite_id, version, updated_at.
- `invites`: id, token_hash, purpose, chat_id, created_by, expires_at, max_uses, uses_count, creates_join_request, revoked_at, version.
- `join_requests`: chat_id, user_id, telegram_request_date, status, reviewed_by, decision_at.
- `membership_events`: actor, action, target, from/to status/expiry, reason, created_at.

Инварианты:

- Не больше одной активной membership для `(user_id, chat_id/community scope)`; повторное погашение не создаёт дубль.
- `membership.version` увеличивается при продлении/смене статуса. Продление — compare-and-swap по `id + version`, только из `active`/`expiring`; ручное `removed` терминально и не перезаписывается продлением.
- `expires_at` хранится в UTC; отображение — в IANA timezone пользователя/администратора. Unix timestamp инвайта — абсолютный, без «локального полуночи».
- Истёкшая membership не даёт доступ к gated-операциям даже при старой кнопке/сессии. Проверка — на сервере, не только при входе.
- `expires_at <= now()` означает истечение по правилу; не путай с «через час».
- Инвайт одноразовый: погашение проверяет `revoked_at`, `expires_at`, `uses_count < max_uses`; `member_limit` у Telegram считает одновременных участников, а не «одно нажатие», и не заменяет серверную идемпотентность.
- Отзыв ссылки не удаляет уже вступивших; истечение срока ссылки не меняет срок членства. Это разные объекты.
- При `creates_join_request=true` нельзя указывать `member_limit`; заявка требует одобрения. Проверяй фактическую схему метода.
- `getChatMember` может быть доступен только когда бот администратор; ошибка не означает «можно». Для gated-доступа неизвестное состояние = запрет/ограничение, не разрешение.
- Храни хэш/непрозрачный идентификатор invite-токена; не логируй полный URL. Показывай ссылку создателю один раз/по необходимости.
- Последнего владельца/администратора нельзя удалить или понизить; owner — из доверенного конфига.

## Состояния и переходы

**Инвайт:** `created → active → redeemed | expired | revoked`.

**Членство:** `invited → pending → active → expiring → expired | left | removed`; `expired/left` → `pending/active` только по явному правилу повторного входа.

| Из | В | Условие |
|---|---|---|
| `pending` | `active` | Инвайт/заявка подтверждены, срок установлен |
| `active` | `expiring` | Приближается срок; напоминание (опционально) |
| `active`/`expiring` | `expired` | `expires_at <= now()`; доступ закрыт |
| `active`/`expiring`/`expired` | `removed` | Ручное удаление с причиной/аудитом; терминально для доступа |
| `expired` | `active` | Разрешённый повторный вход/новая выдача; новая версия, только не из `removed` и не через renewal-CAS |
| `removed` | — | Повторный вход только новой выдачей/инвайтом по политике; автоматического `removed → active` нет |

Продление: реши, считать новый срок от `now()` или от текущего `expires_at`, и зафиксируй это. Продление не должно «воскрешать» истёкшую membership без проверки. Выполняй его как conditional update `WHERE id=? AND version=? AND status IN ('active','expiring')` с увеличением version и audit; если строка уже `removed`, продление отклоняется (или уходит в refund/manual review, если оплата уже подтверждена) и не возвращает доступ. Истечение — идемпотентный job: повторный запуск не удаляет дважды и не удаляет того, кто успел продлиться.

## Транзакции, повторы и идемпотентность

- **Погашение инвайта.** В одной транзакции: загрузить invite с блокировкой, проверить срок/отзыв/лимит, проверить существующую membership, увеличить uses, создать/активировать membership, audit. Повторный callback возвращает существующий результат или понятный отказ, не создаёт второй membership.
- **Продление.** Conditional update по `id + version` и статусу `active`/`expiring`; иначе конфликт/removed, без перезаписи. Ручное удаление и продление в двух транзакциях дают ровно один терминальный исход; после `removed` доступ не возвращается, а подтверждённая оплата продления уходит в refund/manual review по политике. Audit фиксирует from/to и причину.
- **Заявка.** Сохрани pending/reviewed состояние и решение; `approveChatJoinRequest` — внешний side effect. Если он упал/таймаутнул, не показывай «принято» до сверки; повтор должен быть идемпотентен. `ChatJoinRequest.user_chat_id` пригоден для сообщения ограниченное время (по официальной схеме — 5 минут), не используй его как вечный ключ.
- **Истечение.** Durable job с lease: выбрать истёкшие, заблокировать/перечитать, проверить `expires_at` и version, снять доступ/удалить из чата, audit, outbox. Два worker-а не должны удалить дважды. После продления старая задача пропускает участника.
- **Удаление из чата.** Убедись, что у бота есть нужное право (`can_restrict_members`). «Кик» без постоянного бана — это ban с последующим unban по выбранной политике; постоянный ban не снимай автоматически. Не удаляй владельца/последнего администратора.
- **Проверка доступа.** Для критичных операций — актуальная проверка Telegram/БД; кэш membership короткий и с явным TTL. Ошибка/таймаут → deny/limited, не fail-open. После отзыва роли старые кнопки должны снова проверяться.
- **Напоминания.** Durable jobs, уникальность `(membership_id, kind, expires_at)`; после продления старые напоминания отменяются/пересоздаются. Не обещай exactly-once доставку.

## Частые ошибки

- Проверка членства только при входе в бота; старая сессия/кнопка живёт вечно.
- `getChatMember` вернул ошибку — код пропустил пользователя.
- Один invite-link используют дважды; `uses_count` обновляется без блокировки; членство создаётся дважды.
- Отзыв ссылки считают удалением участников.
- Истечение ссылки путают с истечением членства.
- Срок хранения/`expire_date` считают в локальной зоне сервера, а не Unix timestamp/UTC.
- Продление и job истечения гоняются; job удаляет продлённого.
- Продление перезаписывает `removed` или повторно активирует удалённого без CAS/статус-проверки; оплата при этом не возвращается.
- Платное продление не сверяет оплату/возврат; доступ открывается до подтверждения; ручное удаление путают с автоматическим возвратом.
- При `creates_join_request` передают `member_limit` (несовместимо) или не проверяют права `can_invite_users`.
- В чате нет бота-админа; `getChatMember`/approve падают, а UI показывает успех.
- Удаляют последнего владельца/админа или выдают owner через кнопку.
- Полный invite URL и персональные данные попадают в логи.
- Community путают с RBAC: участник одного чата получает доступ к скрытому другому.

## Проверяемые сценарии

1. **Одноразовый инвайт.** Два параллельных погашения одного `max_uses=1` инвайта: ровно одна active membership, `uses_count=1`, второй получает invalid/used; audit один.
2. **Истёкший инвайт.** `expire_date` в прошлом: погашение отклонено; membership не создан.
3. **Идемпотентное истечение.** Два запуска expiry job на одну membership: одно удаление/audit, второй запуск ничего не меняет; внешний kick не дублируется.
4. **Продление против истечения.** Продлить membership до запуска job; job видит новый `expires_at` и не удаляет; доступ сохраняется.
5. **Fail-closed.** `getChatMember`/API таймаутит; gated-действие отклонено или ограничено, в аудите причина; нет выдачи доступа.
6. **Отзыв роли.** Старая кнопка «Продлить/Одобрить» после отзыва права: отказ без изменения; новая проверка на сервере.
7. **Двойное одобрение заявки.** Повторный approve не создаёт второй membership; результат идемпотентен; `user_chat_id` не используется как вечный идентификатор.
8. **Чужой scope.** Участник чата A не получает gated-доступ чата B; community membership не обходит per-chat scope.
9. **Последний владелец.** Попытка удалить/понизить последнего owner/admin отклоняется; other admin не получает extra privilege.
10. **Временная зона/срок.** `expires_at` создан в UTC, показан в IANA zone; граница суток/DST не меняет фактический срок.
11. **Повторный вход.** Политика rejoin: expired/left может/не может вернуться; проверка идемпотентна, старая membership не активна.
12. **Удаление.** Кик без бана применяется по политике; постоянный ban не снимается автоматически; при отсутствии прав операция не выдаёт ложный успех.
13. **Удаление против продления.** Две независимые транзакции: (а) продление первым, затем ручное удаление — итог `removed`, доступа нет; (б) удаление первым, затем продление — продление отклоняется по CAS/статусу, `removed` не перезаписывается; при подтверждённой оплате — refund/manual review по политике. В обоих порядках нет `active` после `removed`, audit без противоречивых событий.

## Опционально и условно

- **Платное членство/подписка** — отдельный платёжный поток, продление, возврат, chargeback; проверь актуальные правила и не открывай доступ до подтверждения. Ручное удаление и refund — разные операции: зафиксируй, возвращается ли оплата, зачитывается ли она и что происходит с уже подтверждённым продлением; после `removed` доступ не открывается, оплата уходит в refund/manual review.
- **Grace period/напоминания** — только если есть согласованная политика; durable jobs.
- **Несколько чатов/уровней доступа** — явная карта chat → scope; не выводи из community автоматически.
- **Mini App/личный кабинет** — для сложного статуса/оплаты; сервер проверяет `initData`.
- **Экспорт участников/аналитика** — отдельное permission, минимизация PII, срок хранения; не добавляй «на всякий случай».
- **Автоодобрение заявок** — только при понятном антиспаме; не заменяет серверную проверку.
