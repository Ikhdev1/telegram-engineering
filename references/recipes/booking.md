# Рецепт: запись на услуги

> Домен: слоты, ресурсы/исполнители, перенос и отмена. Это рецепт, а не готовый бот. Сохраняй существующий стек; не добавляй очередь, Redis или Mini App без подтверждённой потребности.

## Когда брать

- Пользователь выбирает услугу, ресурс/исполнителя и время, а затем подтверждает запись.
- Есть рабочее расписание, длительность, буферы, исключения и ограничение вместимости.
- Нужны перенос, отмена, напоминания или список «Мои записи».

**Не брать**, если продаётся товар без выбора времени (см. [shop.md](shop.md)), ведётся только переписка (см. [support.md](support.md)) или нужен один анонс без резервирования.

## Вопросы, меняющие сценарий

1. **Что именно резервируется:** человек, помещение, оборудование, команда? Может ли быть несколько ресурсов на одну услугу?
2. **Время:** какой IANA timezone у ресурса и у пользователя? Длительность, буфер до/после, минимальный запас, горизонт записи, рабочие дни и исключения. Что делать с несуществующим/двойным локальным временем при DST?
3. **Вместимость:** один ресурс — одна активная запись или несколько (группа/класс)? Можно ли одному клиенту записаться дважды на одно время?
4. **Подтверждение:** мгновенное, ручное, с депозитом? Нужен ли hold (временная бронь) и сколько он живёт?
5. **Отмена/перенос:** кто может, за сколько до начала, взимается ли плата, освобождается ли слот, можно ли перенести на прошедшее время.
6. **Уведомления:** кто получает подтверждение/напоминание; переживает ли напоминание рестарт; как учитывать 429/403 и блокировку бота.
7. **Доступ:** клиент видит только свои записи; оператор — только свой ресурс/филиал; кто меняет расписание и исключения; где аудит.
8. **Успех:** запись создана и видна в списке, слот больше не доступен сверх вместимости, уведомление поставлено в outbox.

## Путь по экранам

```text
Клиент
  Главное меню
    [Записаться]
      Услуга → Ресурс/исполнитель → Дата → Время → Данные → Предпросмотр → Подтвердить → Результат
      [Назад] [Отмена] на шагах выбора; после commit отмена не откатывает запись
    [Мои записи] → Список страницами → Карточка → Перенести / Отменить
    [Настройки] → часовой пояс и напоминания (только личные)

Оператор
  Расписание дня → Слот → Карточка записи → Перенести / Отменить / Отметить неявку
  Исключения и занятость — в пределах своего scope

Администратор / владелец
  Услуги, ресурсы, рабочие часы, исключения, буферы, вместимость, правила отмены, аудит
```

Показывай слот в часовом поясе пользователя, но сохраняй инстант и источник времени. Перед подтверждением покажи дату/время, зону, длительность, цену (если есть) и правила отмены. Пустой день, отсутствие слотов, hold истёк, слот заняли — разные состояния с разными действиями.

## Роли и область объектов

| Действие | Клиент | Оператор | Администратор | Владелец |
|---|---|---|---|---|
| Читать свои записи | Да | Да | Да | Да |
| Читать чужие записи | Нет | Только свой scope/ресурс | В своём tenant/филиале | В своём tenant |
| Создать запись | Себе | По правилам, не обязательно | В scope | В scope |
| Перенести/отменить | Свою, по правилам | Только разрешённую | В scope + аудит | В scope + аудит |
| Менять расписание/исключения | Нет | Нет либо отдельное permission | Да, в scope | Да |
| Менять правила и роли | Нет | Нет | Ограниченный набор | Да |

Проверяй не только роль, но и **объект**: филиал, ресурс, tenant, владельца записи и текущий статус. Запись в чужом филиале не становится доступной из-за admin-кнопки в старом сообщении. Владелец задаётся конфигурацией, не «кто первый нажал `/start`».

## Данные и инварианты

Минимальная модель (адаптируй имена к проекту):

- `resources`: id, tenant_id, timezone IANA, capacity, active.
- `services`: id, duration_min, buffer_before_min, buffer_after_min, active.
- `availability_rules` / `availability_exceptions`: локальные интервалы, дни недели, праздники, разовые исключения.
- `bookings`: id, tenant_id, resource_id, client_id, service_id, starts_at (UTC), ends_at (UTC), status, version, hold_expires_at (nullable), idempotency_key, created_at.
- `booking_events`/audit: actor, действие, from/to, причина, correlation.

Инварианты:

- `starts_at < ends_at`; длительность положительная; буфер не отрицательный.
- Активные интервалы одного ресурса не пересекаются сверх `capacity`. Пересечение считается по полуоткрытому интервалу: `a.starts_at < b.ends_at AND a.ends_at > b.starts_at`. Равенство конца и начала не конфликт.
- Для capacity = 1 — уникальность активного интервала в БД (constraint/exclusion). Для capacity > 1 — атомарный счётчик/слот или транзакция с блокировкой; `SELECT count → INSERT` без блокировки не защищает от гонки.
- Hold (`held`) учитывается как занятость до `hold_expires_at`; истёкший hold должен быть переведён в `expired`/удалён, иначе он либо навсегда блокирует слот, либо обходится неправильно.
- Один активный hold/подтверждение на `idempotency_key`; повтор не создаёт вторую запись.
- Отмена/истечение освобождает вместимость; completed/no-show не освобождают историю, но не блокируют будущие слоты.
- Время хранится в UTC (`timestamptz` в PostgreSQL), а рабочее расписание — в IANA zone ресурса. Отображение — в zone пользователя с явной подписью.
- Не угадывай timezone по языку или стране; пользователь выбирает зону. Если зона не выбрана, показывай подтверждение с zone/offset, а не «серверное время».

### PostgreSQL: защита capacity = 1

Иллюстрация ограничения, не готовый SQL:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
  ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
  )
  WHERE (status IN ('held', 'confirmed'));
```

Это ограничение рассчитано на одну активную запись на ресурс; для capacity > 1 оно не подходит. Предикат не должен зависеть от `now()` (индекс требует immutable-выражения), поэтому истёкшие holds нужно переводить в `expired` отдельным job/транзакцией до новых вставок. Проверь версию PostgreSQL и наличие `btree_gist`.

### SQLite, MySQL и capacity > 1

- Не полагайся на `UNIQUE(starts_at)` — разные интервалы могут пересекаться.
- SQLite: короткая транзакция `BEGIN IMMEDIATE` (или другой подтверждённый режим блокировки), проверка пересечения и вставка внутри неё; один процесс. Не обещай сериализацию нескольких процессов без реальной проверки.
- MySQL/PostgreSQL: блокировка строки ресурса/слота, `SERIALIZABLE` с ретраем конфликтов или таблица слотов с атомарным `UPDATE ... SET remaining = remaining - 1 WHERE remaining > 0`. Выбор зависит от нагрузки и стека.
- Для capacity > 1 протестируй две независимые транзакции, а не последовательный mock.

## Состояния и переходы

| Из | В | Условие |
|---|---|---|
| `draft`/none | `held` | Слот свободен по вместимости, hold не истёк; опционально |
| `held` | `confirmed` | Hold ещё жив, оплата/подтверждение завершены |
| `held` | `expired` | TTL истёк; вместимость освобождена job-ом |
| `confirmed` | `completed` / `no_show` | Время наступило; фиксируй факт, не удаляй историю |
| `confirmed` | `cancelled` | Разрешено по сроку/роли; освобождает слот |
| `confirmed` | `rescheduled` | Атомарно: новый интервал занят, старый освобождён, version +1 |
| `pending_approval` | `confirmed` / `rejected` | Только если подтверждение ручное; TTL/очередь явно заданы |

Запрещено: `expired → confirmed` без новой проверки вместимости; `cancelled → confirmed` как «отмена отмены» без явного правила; перенос, который сначала освобождает старый слот, а потом падает на занятом новом (должна быть одна транзакция/компенсация).

## Транзакции, повторы и идемпотентность

- **Доставка update.** `(bot_id, update_id)` уникален; завершение обработки — в одной транзакции с бизнес-изменением. Не помечай update `done` до создания записи.
- **Смысл операции.** Двойной клик может прийти с новым `update_id`; версия записи, состояние слота и доменный idempotency key защищают повтор.
- **Создание/подтверждение.** В одной транзакции: проверить/занять слот или атомарно уменьшить capacity, записать booking + audit, поставить уведомления в outbox. ACK callback — быстро, до долгих операций; успешный ACK не означает успешную запись.
- **Внешняя оплата/календарь.** Не держи БД-транзакцию открытой на время сети. Для депозита используй provider idempotency key и сверку; запись подтверждается только после проверенного события оплаты. Депозит — опционально.
- **Напоминания.** Durable job + уникальность `(booking_id, kind, scheduled_at)`; повторная доставка Telegram возможна, exactly-once не обещай. После переноса отмени/пересоздай старые напоминания.
- **Outbox.** После commit ставь уведомление в outbox; worker делает send с lease и сохраняет outcome, учитывая 429/`retry_after` и 403. Источник истины для пользователя — запись/экран, а не «сообщение точно доставлено».
- **Таймаут сети.** Сначала считай, что side effect мог выполниться. Не повторяй оплату/создание вслепую; сверься по idempotency key/провайдеру.

## DST и локальное время

- Расписание задаётся локальными интервалами IANA zone. При выборе слота получи **инстанты** начала/конца; `starts_at`/`ends_at` в UTC.
- **Spring-forward gap:** локальное время не существует (например, `Europe/Berlin`, 29.03.2026, 02:30). Сервер должен отклонить такой слот или применить явно документированное правило (перенос/расширение) с подтверждением пользователя; не сдвигай молча.
- **Fall-back fold:** локальное время встречается дважды (например, `Europe/Berlin`, 25.10.2026, 02:30). Нужен явный выбор offset/fold или детерминированная политика; два инстанта различаются, и слоты могут пересечься по-разному.
- Если услуга задана длительностью в локальных минутах, конец через DST может отличаться по UTC от простого `start + minutes`; реши, что именно обещано, и покрой это тестом.
- Переход через полночь, праздники и исключения проверяй на границах; «сегодня» считай в зоне ресурса/пользователя, а не в зоне сервера.
- Тестовые даты DST фиксируй в тестах; не полагайся на «текущую» дату и локальную зону CI.

## Частые ошибки

- «Проверю, что начало не равно началу» — нужно пересечение интервалов, а не равенство.
- `SELECT` занятости и `INSERT` без блокировки/constraint: две гонки создают двойную запись.
- Hold без TTL или без job-а истечения; либо истёкший hold всё ещё блокирует.
- Capacity сравнивают с числом записей, не учитывая отмены/истечения и пересечения.
- Локальное время хранят как UTC без zone/offset; DST ломает отображение и напоминания.
- Часовой пояс угадывают по языку интерфейса.
- Освобождают старый слот при переносе до успешного занятия нового.
- Напоминание отправляется по старому времени после переноса.
- Повторная кнопка «Подтвердить» создаёт вторую запись или списывает депозит второй раз.
- Бот пишет клиенту, хотя тот не начинал диалог/заблокировал бота; 403 не должен выглядеть как успех.
- Оператор меняет чужой ресурс, потому что кнопка была видима; scope не проверен.

## Проверяемые сценарии

Оформляй как integration tests на реальной БД текущего стека; для гонок — две независимые транзакции. Время фиксируй.

1. **Свободный слот при capacity 1.** Записи на `10:00–11:00` ещё нет. Две транзакции одновременно просят `10:30–11:30`. Ожидаемо: ровно одна запись active, вторая получает конфликт/исключение; `count(active)=1`.
   - **Контроль с уже занятым слотом.** Занять `10:00–11:00`; две транзакции одновременно просят `10:30–11:30`. Ожидаемо: **обе** отклонены, `count(active)=1` (только исходная запись), новых booking нет; в audit нет успешного перехода.
2. **Смежные интервалы.** `10:00–11:00` и `11:00–12:00` при capacity 1 обе создаются: полуоткрытый интервал не считает касание пересечением.
3. **Capacity 2.** Две записи на `10:00–11:00` проходят, третья отклоняется; отмена одной снова делает слот доступным.
4. **Двойное подтверждение.** Один и тот же `idempotency_key` с двумя разными `update_id` создаёт одну запись; второй вызов возвращает существующий результат, audit без дубля.
5. **Hold TTL.** Hold истёк; job переводит его в `expired`; слот снова доступен. Прямое `expired → confirmed` отклоняется.
6. **DST gap.** `Europe/Berlin`, `29.03.2026 02:30` локально не существует. Ожидаемо: отказ или документированный перенос с явным подтверждением; в БД нет «тихого» неверного instant.
7. **DST fold.** `Europe/Berlin`, `25.10.2026 02:30` неоднозначно. Ожидаемо: выбор offset/fold; два инстанта различимы; пересечения считаются по instant.
8. **Перенос.** Старый слот освобождён, новый занят, version +1, audit содержит from/to; при конфликте нового слота запись остаётся на старом месте.
9. **Старая кнопка.** После отмены/переноса callback с ожидаемой версией v2 приходит снова. Ожидаемо: конфликт, актуальная карточка, второго перехода нет.
10. **Чужой объект.** Клиент A запрашивает запись клиента B; ответ не раскрывает данные и не меняет состояние. Оператор вне scope получает отказ.
11. **Часовой пояс отображения.** Запись создана в `Asia/Yekaterinburg`, показана в `Europe/Berlin`; UTC instant не изменился, в тексте есть зона.
12. **Напоминание после переноса.** Старое задание отменено/помечено stale; новое создаётся один раз; worker-рестарт не отправляет дубль в пределах выбранной политики.
13. **Недоступность уведомлений.** 403/429 не отменяет запись; статус уведомления отделён от статуса записи; повтор учитывает `retry_after`.

## Опционально и условно

- **Mini App/календарь** — только если реально не хватает inline-навигации: сложный выбор дат, длинная форма, несколько ресурсов. Клиент не авторизует себя; `initData` проверяет сервер.
- **Депозит/оплата** — только по требованию; для цифровой услуги внутри Telegram проверь Stars, для физических/офлайн-услуг — актуальные правила Payments. Не обещай возврат без проверки провайдера.
- **Waitlist, повторяющиеся слоты, групповые занятия, несколько ресурсов, внешний календарь** — отдельные доменные правила и тесты, не «настройка на всякий случай».
- **Redis/outbox worker** — только если напоминания/уведомления должны переживать рестарт; не заменяй ими транзакционную защиту слота.
- **Напоминания/рассылки** — durable jobs, scope, отписка, 429; не добавляй платные broadcast без согласованного бюджета.
