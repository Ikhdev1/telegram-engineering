# Telegram вне одной лички

## Выбери поверхность и полномочия

| Потребность | Подход | Что проверить |
|---|---|---|
| Личная услуга/поддержка | Bot API, private chat | Пользователь начал взаимодействие/дал допустимое право записи; обычный бот не может писать любому по username |
| Анонсы/посты | Bot API, channel | Право публикации и нужных медиа; согласование перед публикацией |
| Общение/модерация | Bot API, group/supergroup | Privacy mode, admin rights, темы, allowed_updates, контекст sender |
| Несколько связанных чатов | Telegram Community + per-chat policy | Видимость чатов и добавление участников; членство не равно роли в продукте |
| Персональный ответ внутри группы | Ephemeral API | Условия события/15 секунд, адресат, версия SDK; не гарантировать доставку |
| Ответ в чужом чате по вызову | Guest Mode | Настройка, guest_query_id, разрешённый ответ; это не доступ к истории |
| Работа от подключённого аккаунта | Business/Secretary bot при достаточных правах | business_connection_id и актуальные BusinessBotRights; не путать с user session |
| Полноценный клиент своего аккаунта | Telegram API/TDLib (MTProto) | Явное разрешение, api_id/api_hash и локальная сессия; не выдавать Bot API token за user auth |

Bot API не даёт произвольный доступ ко всей истории, диалогам и контактам аккаунта. Не обещай массовый DM по чужим username или выгрузку всех участников средствами, которых нет в нужном API. Не выбирай MTProto только ради меню/постов, которые делает бот. При запросе аккаунт-автоматизации сначала проверь, достаточно ли Business Bot с ограниченными правами.

## Клиентский Telegram и публикации

Для просьбы «оформить пост» верни сам текст/структуру и способ размещения: вручную через редактор или через конкретный API. Не запускай бота, не публикуй и не меняй настройки чатов без соответствующей задачи. В статье от июля 2026 редактор rich-постов доступен Premium-пользователям; актуальную доступность уточняй по официальным материалам и установленному клиенту, а не объявляй вечным требованием для всех ботов.

В канале CTA обычно ведёт URL/deep link в личку: `https://t.me/BOT_USERNAME?start=...`. Payload: до 64 символов, допустимы A-Z/a-z/0-9/_/-. Он недоверенный; для account linking и доступа используй серверный одноразовый ключ с подтверждением. При пересылке не теряй смысл CTA, дату, авторство/источник и правила конфиденциальности.

Если нужно расписание публикаций — храни job/payload/target/timezone/status в durable storage и явно подтверждай целевой канал. Бот не редактирует произвольные чужие посты только потому, что знает message_id. Для channel direct messages передавай `direct_messages_topic_id` по контракту метода; это не `message_thread_id` обычного форума.

## Группы, топики, membership

Privacy mode уменьшает поток входящих сообщений, но **не означает «бот ничего не читает»**: есть команды, ответы, service messages и другие описанные случаи. Сохраняй его включённым, если работа не требует полного потока. В новых API есть bot-to-bot/guest исключения: абсолютное «боты никогда не видят ботов» из старого FAQ не используй.

Для тем сохраняй `message_thread_id` и верный chat context; сообщения в общий чат и в тему не взаимозаменяемы. Сервисный переход group → supergroup меняет chat id: обработай migration fields/ResponseParameters и связанные настройки, если бот работает с такими чатами. `sender_chat`/анонимный админ — не обычный `from.id`; не наделяй таким сообщением неизвестного человека правами owner.

Для moderation/join requests запроси минимальные Telegram-права: удаление не требует выдачи права назначения админов. Обрабатывай `my_chat_member` для потери доступа; `chat_member` нужно явно включить в allowed_updates при необходимости. Проверка другого пользователя через `getChatMember` гарантируется лишь когда бот администратор. Ошибка проверки не превращается в разрешение. Если продукт использует membership как gate, определи freshness/истечение и поведение при выходе; не кешируй допуск навечно.

## Сообщества

Сообщество объединяет группы, каналы и ботов, но не является автоматическим объединением всех application roles. По статье чаты могут быть видимы всем участникам либо скрыты; возможность добавления чатов настраивается. Проверь, кто может добавлять/предлагать чаты. Для продукта храни понятную карту chat → scope; не позволяй переносу чата случайно открыть старые приватные данные.

В Bot API снимка есть `Community`, `ChatFullInfo.community`, события `community_chat_added`, `community_chat_removed`, `community_chat_joined`. Наличие типов не означает наличие любого воображаемого метода `createCommunity`: проверяй список методов. Различай ручные действия администратора в приложении и автоматизируемые методы.

## Ephemeral: персональное меню в группе

[Контракт](https://core.telegram.org/bots/api.md#ephemeral-messages-and-commands), [EphemeralMessageParameters](https://core.telegram.org/bots/api/types/ephemeralmessageparameters.md).

С Bot API 10.3 в методе отправки используется **`ephemeral_message_parameters`**, внутри `receiver_user_id` и при необходимости `callback_query_id`. Не используй заменённые top-level поля из 10.2. Для входящей ephemeral-команды установи `BotCommand.is_ephemeral=true` через список команд; это не то же, что silent notification.

Не-админ может отправить ответ в течение **15 секунд** после допустимого действия, указав callback_query_id либо `reply_parameters.ephemeral_message_id`. Ответ привязан к вызвавшему клиенту. Бот-администратор может отправлять non-bot участнику чата без этого события в любое время. В обоих случаях доставка **не гарантируется**, особенно офлайн; сообщение может исчезнуть со временем/перезапуском клиента. Это не хранилище подтверждений и не журнал действий.

Пример двух отдельных POST после полученного callback; значения демонстрационные, в реализации берутся из проверенного update:

`answerCallbackQuery`:
```json
{"callback_query_id": "incoming-query-id"}
```

`sendMessage` в тот же group chat, не дожидаясь долгой работы:
```json
{
  "chat_id": -1001234567890,
  "ephemeral_message_parameters": {
    "receiver_user_id": 123456789,
    "callback_query_id": "incoming-query-id"
  },
  "text": "Ваше меню",
  "reply_markup": {"inline_keyboard": [
    [{"text": "Мои заявки", "callback_data": "my:requests"}]
  ]}
}
```

Адресат берётся из `callback_query.from.id`, не из пользовательского payload; chat из проверенного контекста. ACK не заменяет ephemeral send. Для rich-ответа используй `sendRichMessage` с таким же `ephemeral_message_parameters` и `rich_message`.

`replace_callback_query_message=true` показывает приватный overlay вместо исходного сообщения для пользователя; он должен быть false для callbacks уже из ephemeral-сообщения. Их меняют через `editEphemeralMessageText/Media/Caption/ReplyMarkup` и `ephemeral_message_id` по точной схеме; не редактируют публичный message_id. Обычный `selective` у reply keyboard и `disable_notification` не скрывают само сообщение от остальных.

В техническом ответе про персональное меню явно назови две разные операции: **`editMessageText` исходного группового сообщения меняет его для всех; персональное меню меняется через `editEphemeralMessage*` по ephemeral_message_id**. Такое предложение предотвращает утечку при последующей реализации; одного описания приватного overlay недостаточно.

Если доставка критична, сохраняй результат в БД и предоставляй доступный пользователю устойчивый экран в личке. Не публикуй приватное сообщение в группе как «fallback». Переход в личку по deep link — безопасный вариант при явно неподдерживаемой поверхности; не переключай незаметно новый API на публичный ответ.

## Сессия аккаунта (при явном запросе)

Для TDLib/MTProto следуй актуальным официальным auth/updates правилам. OTP/2FA вводится оператором локально в доверенном процессе; не проси его в переписке. Session file/string и api_hash — секреты, доступ к аккаунту не ограничивается ботом. Не сохраняй их в исходниках и не публикуй при диагностике. Обрабатывай FloodWait и отключение сессии, не обходи ограничения массовой рассылкой. Не трогай работающий user client и не завершай его сессию для теста.
